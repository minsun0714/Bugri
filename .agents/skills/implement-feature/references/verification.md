# 검증과 실패 처리

기능 구현·수정·리팩터링·설정 변경 및 PR 준비에서 사용하는 공통 검증 기준이다. 문서만 바뀌면 아래 예외를 적용한다.

## 코드 변경

- 비즈니스 로직 변경은 단위 테스트, UI 동작 변경은 컴포넌트 테스트, 사용자 흐름 변경은 Playwright E2E로 검증한다. 새 기능에는 관련 테스트를 포함한다.
- 관련 검사를 먼저 실행한다: `npm run lint`, `npx tsc --noEmit`, `npm test`(Jest + React Testing Library), `npx playwright test`(구성된 E2E).
- 마지막 코드 변경 후 **해당 워크트리에서 `npm run verify`를 실행**한다. 현재 pipeline은 lint → TypeScript → Jest → production build → Playwright다. 개별 검사 성공만으로 전체 검증 완료라고 기록하지 않는다.
- 충돌 해결·후속 코드 변경·통합 후에는 전체 검증을 다시 실행한다. 이전 결과가 변경된 코드를 검증하지 않는다.
- Node 버전·생성 타입·포트 등 실행 환경은 [Hook 문서](../../../../docs/HOOKS.md)와 프로젝트 설정을 따른다. 다른 워크트리가 포트를 사용하면 `PLAYWRIGHT_PORT=3108 npm run verify`처럼 빈 포트를 지정한다. 다른 서버를 종료하거나 재사용해 통과시키지 않는다.

## 실패 처리

1. 실패 원인을 분석하고 구현을 수정한 뒤 실패한 검사를 다시 실행한다. 테스트가 승인된 요구사항과 충돌하는 경우에만 기대값을 고친다.
2. 수정·재실행은 최대 3회 수행한다. 관련 검사가 통과하면 전체 검증을 다시 실행한다. 미구현 상태의 의도한 첫 실패는 재시도 횟수에서 제외하지만, 전체 검증에서 다른 실패가 나와도 횟수를 초기화하지 않는다.
3. 3회 후에도 해결되지 않으면 중단하고 원인·시도 내용·남은 차단 요인을 보고한다. 도구 부재·환경 차단으로 실행하지 못한 검사도 이유·검증 한계·해제 조건을 기록한다.
4. 검사를 생략하거나 약화해 통과시키지 않는다. 실행하지 않은 검사를 성공으로 기록하지 않는다. 실패·미실행 필수 검사가 남아 있으면 구현 작업을 DONE으로 표시하지 않고 PR은 Draft로 유지한다.

## 문서만 변경한 경우

- `git diff --check`와 문서 정합성 검토로 검증한다. 링크·요구사항·단계 구분·변경된 규칙의 적용 범위를 확인한다.
- 문서 전용 변경이므로 기능 pipeline을 실행하지 않았음을 기록한다. 스킬을 수정했다면 frontmatter·참조 경로·적용 조건도 검증한다.
- 이 예외는 구현 검증 완료로 간주하지 않으며, 구현 작업을 DONE으로 표시하는 근거가 아니다. 코드·설정 변경이 섞이면 이 예외를 적용하지 않는다.

## 기록

실행 명령·실제 결과·미실행 항목·제약을 남긴다. PR에는 검증한 커밋도 기록한다. Hook이 검증을 실행했다면 실제 성공 로그를 근거로 삼고, 수동 실행과 중복된 성공을 가정하지 않는다.
