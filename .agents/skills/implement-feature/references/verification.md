# 검증과 실패 처리

기능·수정·리팩터링·설정·PR 준비의 단일 검증 기준이다. 변경 파일 수가 아니라 동작과 영향 범위로 선택한다.

## 변경별 필수 검증

| 변경 | 로컬 완료 전 검증 |
| --- | --- |
| 문서만 | 문서 정합성·링크·git diff --check. 스킬은 frontmatter·참조·적용 조건도 확인 |
| 문구·여백·색상 등 동작 없는 UI | 변경 파일 lint/포맷 검사, 해당 화면 PC·모바일 확인. 의미 있는 UI는 독립 UX/UI 리뷰 유지 |
| 페이지 이동·컴포넌트 동작 | 변경 파일 정적 검사, 전체 타입 검사, 관련 단위/컴포넌트 테스트와 해당 사용자 흐름 E2E |
| API·저장·보상·공통 컴포넌트·빌드/실행 설정 | 관련 검사 우선, 영향 받는 사용처 확인, 아래 최종 검증 기준 적용 |

- 관련 검사는 변경 동작과 직접 의존하는 사용처·회귀 위험으로 선정하고 이유를 기록한다. 영향 범위가 불명확하면 넓혀 검사한다. 기존 테스트를 약화하거나 실패를 제외하지 않는다.
- Jest는 관련 테스트 파일, E2E는 `npm run test:e2e -- <관련 spec 경로>`로 실행할 수 있다. 타입 검사는 `npm run typecheck`, 전체 검증은 `npm run verify`다. 새 기능의 동작 테스트와 기존 TDD 원칙은 유지한다.
- 작은 변경은 위 관련 검증으로 로컬 완료·커밋할 수 있다. 이를 전체 검증 통과로 표현하지 않는다.

## E2E 선택

- E2E는 변경한 동작과 그 동작을 사용하는 흐름의 spec을 선택한다. 파일 경로만으로 판단하지 않고, 변경한 공통 컴포넌트·API·스타일·의존성의 사용처를 확인한다. 영향이 불명확하면 범위를 넓힌다.
- 실행 전에 선택한 spec과 제외한 spec, 제외 근거를 검증 기록에 남긴다. spec이 여러 기능을 함께 검사하면 관련 흐름이 포함된 파일을 유지한다. 기존 테스트를 삭제하거나 assertion·timeout을 완화하지 않는다.
- `npm run verify`는 모든 E2E를 호출한다. 일부 spec만 실행했다면 이를 `npm run verify` 전체 통과로 표현하지 않는다.

## 최종 검증 시점과 결과 재사용

- 코드 변경 PR 최종 준비, 코드 충돌 해결·최신 코드 통합, 위 고위험 변경의 완료 시 lint·전체 타입·전체 Jest·도구 테스트·production build를 확인한다. E2E는 전체 spec을 실행한다. 리뷰·수정이 끝난 뒤 해당 워크트리에서 한 번 수행하며 유효한 기존 결과는 재사용한다.
- 수동 최종 검사 명령은 `npm run lint`, `npm run typecheck`, `npm test -- --runInBand`, `npm run test:tools`, `npm run build`, `npm run test:e2e`다. 한 번에 전체를 실행하려면 `npm run verify`를 사용한다.
- 작업 중 매 수정마다 전체 검증을 실행하지 않는다. 선정된 필수 검증 전이라면 PR은 Draft이며 로컬 완료와 병합 준비 완료를 구분한다.
- 코드·테스트·의존성·빌드/실행 설정과 검증 환경이 검증 당시와 같으면 성공 결과를 재사용한다. 기록·PR 본문 등 문서만 변경되거나 동일 내용을 커밋했다는 이유로 다시 실행하지 않는다. 검증한 버전과 차이가 문서뿐이라는 근거를 남긴다.
- 문서 전용 PR이나 문서만 충돌 해결한 경우에는 문서 검증만 수행한다. 단, 통합으로 코드·테스트·설정이 달라졌으면 문서 충돌만 있었더라도 위 최종 검증을 수행한다.
- Node 22.23.3과 [Hook·포트 지침](../../../../docs/HOOKS.md)을 따른다. 다른 작업자의 서버·검증 프로세스를 중단하거나 재사용하지 않는다.

## 실패 처리

1. 실패 원인을 분석하고 수정한 뒤 실패한 검사와 수정 영향 검사를 먼저 재실행한다. 승인된 요구사항과 충돌하는 경우에만 테스트 기대값을 바꾼다.
2. 수정·재실행은 최대 3회다. 같은 작업에서 검사 종류가 달라져도 한도를 초기화하지 않는다. TDD의 의도한 최초 실패는 제외한다.
3. 관련 검사가 통과하면 해당 변경에 전체 검증이 필요한 시점인지 판단한다. 필요한 경우에만 최종 전체 검증한다.
4. 한도 소진·도구 부재·환경 차단은 원인·시도·남은 검사를 보고한다. 필수 미통과 검사가 남으면 해당 완료 단계로 표시하지 않고 PR은 Draft로 유지한다.

## 기록과 Hook

- 변경 분류·선정 이유·명령·실제 결과·검증 버전/환경·미실행 범위와 이유를 기록한다. 영향 범위 검증 통과와 모든 테스트의 전체 통과를 구분한다. 새 제외 기준으로 과거 실패를 삭제하거나 성공으로 바꾸지 않는다.
- 문서 전용 작업은 기능 pipeline·Hook을 실행하지 않는다.
- 전체 검증은 수동 실행 또는 Hook 중 하나로 수행한다. 같은 최종 상태에서 중복 실행하지 않는다. Hook은 전체 검증이 필요한 최종 시점에만 활성화한다.
- 이미 활성화된 Hook이나 실행 중 검사를 임의로 중단·성공 처리하지 않는다. 담당 에이전트가 상태·로그를 확인하고 기존 실행을 마친 뒤 이후 검증에 새 기준을 적용한다.
