# 기능 구현

공통 원칙은 [AGENTS.md](../../../AGENTS.md)를 따른다. 기존 사용자 승인 범위 안에서 진행하며, 문서·검토 요청만으로 애플리케이션을 수정하지 않는다.

1. [PRD](../../../docs/PRD.md), [아키텍처](../../../docs/ARCHITECTURE.md), [TASKS](../../../docs/TASKS.md)와 관련 코드를 확인한다. 대상 TASKS ID·REQ/AC·선행 조건을 식별하고 확정·제안·미결정을 구분한다. 후속 제품 요구사항을 현재 구현으로 확대하지 않는다. API 작업은 [API 문서](../../../docs/API.md), 코드 작성은 [코딩 규칙](../../../docs/CODING_CONVENTIONS.md)을 함께 읽는다.
2. UI 작업은 아래 디자인 시스템 사용 규칙과 재사용할 컴포넌트를 먼저 확인한다. 수정 파일·범위와 검증 계획을 짧게 제시하고 해당 작업을 IN_PROGRESS로 표시한다. 구현에 꼭 필요한 미결정이 있으면 해당 부분을 보류해 확인하되, 이미 승인된 범위를 다시 승인받지 않는다. 병렬 작업이 명시적으로 허용되어 분담할 때는 파일 소유권을 지정하고 공유 계약·패키지·전역 설정을 통합 담당자와 조율한다.
3. 새 기능에는 관련 테스트를 포함한다. 비즈니스 로직·UI 동작 변경은 확정된 요구사항/API 계약으로 정상·주요 예외 테스트를 먼저 작성한다. 새 테스트를 실행해 미구현으로 인한 실패를 확인한다. 환경/설정 오류는 의도한 실패로 간주하지 않는다. 단순 문구·스타일·문서 수정에는 테스트 우선 절차를 강제하지 않는다.
4. 요청한 기능을 구현하고 관련 테스트를 실행·수정한다. Mock 동작과 2단계의 실제 보안·영속성·동시성 보장을 구분한다. 범위가 달라지면 관련 문서도 일치시키며 제품 요구사항을 임의로 바꾸지 않는다.
5. 의미 있는 UI 구현·수정이 끝나면 [ux-review-loop](../ux-review-loop/SKILL.md)에 따라 새 컨텍스트의 독립 UX·UI sub-agent가 각각 사용자 목표 기준으로 문제를 목록화하고, 수정·재검증을 최대 3회 수행한다. `docs/ux-reviews/<TASK_ID>.md`에 관점별 근거·문제 처리·회차 결과를 남긴다. 근거 없는 ‘문제 없음’이나 핵심 상태 미확인을 UX 완료로 처리하지 않는다. 이후 [검증·실패 처리](references/verification.md)에 따라 변경 위험도와 완료 단계에 맞는 검증을 수행한다. 실패 재시도 한도와 미실행/차단 기록을 지킨다.
6. 변경 파일·동작·실행 명령·결과·남은 제약을 보고하고 TASKS의 상태·근거를 일치시킨다. 구현과 필수 검증을 모두 마친 작업만 DONE으로 표시한다.

## UI·비즈니스 규칙·API 상태 분리

- 화면이 바뀌어도 유지되는 채점·복습 일정·학습일 규칙은 React 밖의 순수 함수 또는 서비스에 둔다. 저장된 기록에 의존하는 중복 집계·소유권 판단은 API 뒤 서비스가 결정한다. 훅의 상태나 버튼 비활성화로 무결성을 보장하지 않는다.
- 컴포넌트는 표시와 이벤트 연결을 맡는다. 간단한 모달·탭·입력 상태와 표시용 변환은 가까이 두어도 된다. 모든 함수를 훅으로 옮기거나 모든 기능에 동일한 계층을 강제하지 않는다.
- 여러 입력 상태·검증·비동기 동작을 조율하는 흐름은 기능별 custom hook으로 분리한다. 훅은 순수 규칙과 API 훅을 조합하며, JSX·저장소 접근·채점 규칙을 한 훅에 섞지 않는다. `canSubmit`처럼 계산 가능한 값은 별도 state로 복제하지 않는다.
- 제품 UI의 API 연결에는 TanStack Query를 사용한다. 첫 API 연동 기능에서 의존성과 안정적인 QueryClientProvider를 함께 도입한다. API가 없는 공통 UI 전시·단순 로컬 상태만을 위해 설치하거나 가짜 요청을 만들지 않는다. Promise 기반 브라우저 Mock 클라이언트도 같은 경계로 사용한다.
- 기능별 `useQuery`·`useMutation` 래퍼에 쿼리 키, 타입이 정의된 API 클라이언트 호출, 캐시 갱신을 모은다. UI/훅은 Mock 파일·localStorage·서비스를 직접 호출하지 않는다. 독립적인 입력 검증 순수 함수 사용은 허용한다. HTTP 전송은 API 클라이언트, 제품 규칙은 API 뒤 서비스가 담당한다.
- 사용자별 데이터의 키에 사용자 식별자와 조회 조건을 포함한다. 사용자 전환 시 이전 캐시·진행 중 요청 결과·로컬 입력이 새 사용자에게 섞이지 않게 처리한다. 캐시는 인증 수단이 아니다.
- 변경 성공 후 상세와 관련 목록을 함께 갱신한다. 예: 답안 제출 → Attempt·학습 기록·풀이 내역, 퀴즈 저장 → 내 퀴즈 목록·메모의 퀴즈 목록. 필요한 무효화 대상을 명시하며 오류·재시도·staleTime·자동 재조회는 해당 계약에 맞춘다. 상태를 변경하는 동작을 자동 재조회 query로 구현하지 않는다.
- 제출 실패 시 입력을 보존하고 API 오류를 구분한다. 사용자·Attempt 전환 시 입력과 mutation 결과의 초기화 경계를 정한다. 제출 가능 여부는 UX 검증이며 API에서도 요청을 검증한다. 정답·해설은 제출 전 캐시·HTML에 포함하지 않는다.
- 예시 구조: 컴포넌트 → 필요할 때 기능 흐름 훅(`useQuizSolving`) → API 훅(`useAttempt`, `useSubmitAnswer`) → 타입 API 클라이언트 → Mock 어댑터/향후 Spring Boot 서비스. 예시의 객관식·타입·오류 문구를 제품 계약으로 복사하지 않고 PRD/API를 확인한다.
- 검증은 규칙의 정상·예외, 훅을 사용하는 UI 동작, API 변경 후 관련 데이터 갱신과 사용자/풀이 전환을 대상으로 한다. 훅을 추출했다는 구조 자체를 검증하는 테스트는 만들지 않는다.

## 검증 Hook을 사용할 때

일부 E2E spec만 선택해 실행하려면 [검증 지침](references/verification.md)의 수동 명령을 사용하고 Hook을 활성화하지 않는다. 현재 Hook은 spec 선택·worker 인자를 지원하지 않는다. [Hook 사용법](../../../docs/HOOKS.md)을 읽고 Hook 기본 명령으로 전체 검증할 필요가 있는 최종 시점에만 `python3 -B scripts/hooks/verify_stop.py arm TASK_ID`로 활성화한다. Hook의 실제 로드·신뢰가 확인되지 않은 환경에서는 검증 지침을 직접 수행한다. Hook을 사용해도 관련 테스트는 직접 실행하며 마지막 전체 검증은 Hook이 실행한다. 성공 후 코드가 바뀌면 재검증한다. 환경 차단·사용자 중단은 `blocked "사유"`로 기록하고 성공으로 취급하지 않는다. 문서 작업에는 활성화하지 않는다.

## 디자인 시스템 사용

- 의미 있는 UI 작업은 UX 구조 검토 후 별도 [UI 디자이너](../ui-designer/SKILL.md) sub-agent에게 시각 설계를 위임하고 구현한다. 이 지침은 설계 위임을 명시적으로 요구하며 별도 승인 단계는 추가하지 않는다.

- 화면 구조·사용자 흐름·인터랙션을 설계하거나 변경할 때는 [ux-designer](../ux-designer/SKILL.md)의 역할과 판단 기준을 적용한다. 이 참조가 별도 설계 승인이나 요청하지 않은 화면 재설계를 요구하지는 않는다.
- UI 구현 전 [공통 UI](../../../src/components/ui/)의 실제 props·상태를 확인하고 먼저 재사용한다. 기본 요소는 `index.tsx`, 태그 입력은 `tag-input.tsx`, Markdown 입력은 `markdown-editor.tsx`, 코드 표시는 `code-block.tsx`, 푸터는 `footer.tsx`를 사용한다. 동일한 역할의 컴포넌트를 기능 폴더에 복제하지 않는다.
- 색상·폰트·애니메이션은 [globals.css](../../../src/app/globals.css)의 `@theme` 토큰을 기준으로 삼는다. Tailwind와 [공통 클래스 조합](../../../src/components/ui/styles.ts)을 사용하고, 화면마다 별도 색상 체계·전역 CSS·CSS-in-JS를 만들지 않는다.
- 필요한 상태가 없으면 기존 컴포넌트의 variant나 props로 확장한다. 기존 사용처에 맞지 않는 책임까지 억지로 합치지는 않으며, 새 공통 요소가 필요한 경우 `src/components/ui`에 추가한다. 공통 변경은 기존 화면과 관련 테스트에서도 확인한다.
- [홈 전시](../../../src/components/showcase/design-showcase.tsx)는 조합·시각 상태를 확인하는 예시다. 전시용 데이터·문구·인터랙션을 실제 제품 로직으로 복사하거나, 일반 기능 화면에서 showcase 모듈을 import하지 않는다. 헤더·모바일 메뉴는 `src/components/ui/header.tsx`와 `mobile-navigation.tsx`를 재사용한다. 기본 홈에서도 이 헤더와 공통 푸터를 유지하며 본문 전시만 숨긴다.
- 카드마다 제목 아래 소개 문장을 자동으로 붙이지 않는다. 콘텐츠·상태·다음 행동을 우선 배치하고, 입력 도움말·오류·빈 상태처럼 판단에 필요한 안내만 둔다. 현재 시안의 모든 화면 구성을 확정 제품 요구사항으로 간주하지 않는다.
- 키보드 포커스, 로딩·비활성·오류 상태, 모바일 줄바꿈과 메뉴 동작을 유지한다. 데이터·저장·API 처리는 공통 UI와 분리하고, UI에는 props와 이벤트로 연결한다.

## TASK 기록 위치

`docs/TASKS.md`는 탐색 안내다. 관련 `docs/tasks/<TASK-ID>.md`에서 상태·선행 조건·검증 근거를 확인하고 갱신한다. 신규 TASK는 고유 ID의 새 파일로 추가하며 중앙 목록을 수정하지 않는다. 기존 정책 변경은 기준 문서를 직접 수정한다.
