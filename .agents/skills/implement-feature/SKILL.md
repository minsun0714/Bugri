# 기능 구현

공통 규칙은 저장소 루트의 `AGENTS.md`를 따른다. 사용자가 명시적으로 구현을 요청하지 않았다면 문서·분석 범위에 머물고 코드 수정에 착수하지 않는다.

Codex Stop Hook을 사용하는 기능 작업은 [Hook 사용법](../../../docs/HOOKS.md)을 확인하고 작업 시작 시 `python3 -B scripts/hooks/verify_stop.py arm TASK_ID`로 활성화한다. Hook이 로드·신뢰되지 않은 환경에서는 아래 검증 절차를 직접 수행한다. Hook 사용 시에도 관련 테스트는 직접 실행하며, 마지막 전체 검증은 Stop Hook이 실행한다. 성공 후 추가 코드 변경은 재검증한다. 환경 차단이나 사용자 중단 요청은 `blocked "사유"`로 기록하고 성공으로 간주하지 않는다.

1. `docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/TASKS.md`와 관련 코드를 읽고 확정 사항·제안·미결정을 구분한다.
2. 대상 REQ/AC 번호와 TASKS 작업 ID, 선행 조건을 확인한다. 후속 제품 요구사항을 MVP 구현으로 확대하지 않는다.
3. UI 작업은 아래 디자인 시스템 사용 규칙을 먼저 확인하고, 재사용할 컴포넌트·수정 범위·검증 계획을 짧게 제시한다. 구현에 꼭 필요한 결정이 없으면 해당 부분을 보류하고 확인한다. 이미 승인된 범위를 다시 승인받지는 않는다.
4. 해당 작업을 IN_PROGRESS로 표시하고, 비즈니스 로직과 UI 동작 변경은 구현 전에 확정된 REQ/AC와 API 계약을 기준으로 정상·주요 예외 테스트를 작성한다. 로직은 단위 테스트, UI 동작은 컴포넌트 테스트, 사용자 흐름은 Playwright E2E로 검증한다. 단순 문구·스타일·문서 수정에는 테스트 우선 절차를 강제하지 않는다.
5. 새 테스트를 실행해 기능 미구현으로 의도한 실패가 발생하는지 확인한다. 환경·설정 오류를 의도한 실패로 간주하지 말고 먼저 해결한다. 테스트 도구가 없거나 환경 문제로 검증할 수 없으면 사유·검증 한계·해제 조건을 기록한다.
6. 테스트를 통과하도록 요청된 기능을 구현하고, 코드를 정리한 뒤 관련 테스트를 다시 실행한다. 범위가 달라지면 관련 문서도 일치시킨다. 1단계에서는 Mock 동작을 검증하며, 실제 보안·동시성·트랜잭션 보장은 2단계 검증 대상으로 구분한다.
7. 마지막 코드 변경 후 해당 워크트리에서 `npm run verify`를 실행한다. 검증 실패 시 원인 분석 → 구현 수정 → 실패한 검사 재실행을 최대 3회 수행하고, 관련 검사가 통과하면 전체 검증을 다시 실행한다. 미구현 상태의 의도한 첫 실패는 수정 재시도 횟수에 포함하지 않는다. 전체 검증에서 다른 실패가 발견되어도 재시도 횟수를 초기화하지 않는다. 3회 후에도 해결되지 않으면 중단하고 원인·시도 내용·남은 차단 요인을 보고한다. 테스트가 승인된 요구사항과 충돌하는 경우를 제외하고 기대값을 바꾸지 않으며, 검사를 생략하거나 약화해 통과시키지 않는다.
8. 변경 파일·동작, 실행 명령과 결과, 미실행 검사·남은 제약을 보고한다. 실행하지 않은 테스트를 성공으로 보고하지 않는다.
9. 최종 보고와 일치하도록 TASKS.md 상태와 검증 근거를 반영한다. 구현과 필수 검증을 모두 마친 작업만 DONE으로 표시한다.

## 디자인 시스템 사용

- UI 구현 전 [공통 UI](../../../src/components/ui/)의 실제 props·상태를 확인하고 먼저 재사용한다. 기본 요소는 `index.tsx`, 태그 입력은 `tag-input.tsx`, Markdown 입력은 `markdown-editor.tsx`, 코드 표시는 `code-block.tsx`, 푸터는 `footer.tsx`를 사용한다. 동일한 역할의 컴포넌트를 기능 폴더에 복제하지 않는다.
- 색상·폰트·애니메이션은 [globals.css](../../../src/app/globals.css)의 `@theme` 토큰을 기준으로 삼는다. Tailwind와 [공통 클래스 조합](../../../src/components/ui/styles.ts)을 사용하고, 화면마다 별도 색상 체계·전역 CSS·CSS-in-JS를 만들지 않는다.
- 필요한 상태가 없으면 기존 컴포넌트의 variant나 props로 확장한다. 기존 사용처에 맞지 않는 책임까지 억지로 합치지는 않으며, 새 공통 요소가 필요한 경우 `src/components/ui`에 추가한다. 공통 변경은 기존 화면과 관련 테스트에서도 확인한다.
- [홈 전시](../../../src/components/showcase/design-showcase.tsx)는 조합·시각 상태를 확인하는 예시다. 전시용 데이터·문구·인터랙션을 실제 제품 로직으로 복사하거나, 일반 기능 화면에서 showcase 모듈을 import하지 않는다. 헤더·모바일 메뉴는 `src/components/ui/header.tsx`와 `mobile-navigation.tsx`를 재사용한다. 기본 홈에서도 이 헤더와 공통 푸터를 유지하며 본문 전시만 숨긴다.
- 카드마다 제목 아래 소개 문장을 자동으로 붙이지 않는다. 콘텐츠·상태·다음 행동을 우선 배치하고, 입력 도움말·오류·빈 상태처럼 판단에 필요한 안내만 둔다. 현재 시안의 모든 화면 구성을 확정 제품 요구사항으로 간주하지 않는다.
- 키보드 포커스, 로딩·비활성·오류 상태, 모바일 줄바꿈과 메뉴 동작을 유지한다. 데이터·저장·API 처리는 공통 UI와 분리하고, UI에는 props와 이벤트로 연결한다.
