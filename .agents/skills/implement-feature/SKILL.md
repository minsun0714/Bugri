# 기능 구현

공통 규칙은 저장소 루트의 `AGENTS.md`를 따른다. 사용자가 명시적으로 구현을 요청하지 않았다면 문서·분석 범위에 머물고 코드 수정에 착수하지 않는다.

1. `docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/TASKS.md`와 관련 코드를 읽고 확정 사항·제안·미결정을 구분한다.
2. 대상 REQ/AC 번호와 TASKS 작업 ID, 선행 조건을 확인한다. 후속 제품 요구사항을 MVP 구현으로 확대하지 않는다.
3. 수정 범위와 검증 계획을 짧게 제시한다. 구현에 꼭 필요한 결정이 없으면 해당 부분을 보류하고 확인한다. 이미 승인된 범위를 다시 승인받지는 않는다.
4. 해당 작업을 IN_PROGRESS로 표시하고, 비즈니스 로직과 UI 동작 변경은 구현 전에 확정된 REQ/AC와 API 계약을 기준으로 정상·주요 예외 테스트를 작성한다. 로직은 단위 테스트, UI 동작은 컴포넌트 테스트, 사용자 흐름은 Playwright E2E로 검증한다. 단순 문구·스타일·문서 수정에는 테스트 우선 절차를 강제하지 않는다.
5. 새 테스트를 실행해 기능 미구현으로 의도한 실패가 발생하는지 확인한다. 환경·설정 오류를 의도한 실패로 간주하지 말고 먼저 해결한다. 테스트 도구가 없거나 환경 문제로 검증할 수 없으면 사유·검증 한계·해제 조건을 기록한다.
6. 테스트를 통과하도록 요청된 기능을 구현하고, 코드를 정리한 뒤 관련 테스트를 다시 실행한다. 범위가 달라지면 관련 문서도 일치시킨다. 1단계에서는 Mock 동작을 검증하며, 실제 보안·동시성·트랜잭션 보장은 2단계 검증 대상으로 구분한다.
7. 마지막 코드 변경 후 해당 워크트리에서 `npm run verify`를 실행한다. 검증 실패 시 원인 분석 → 구현 수정 → 실패한 검사 재실행을 최대 3회 수행하고, 관련 검사가 통과하면 전체 검증을 다시 실행한다. 미구현 상태의 의도한 첫 실패는 수정 재시도 횟수에 포함하지 않는다. 전체 검증에서 다른 실패가 발견되어도 재시도 횟수를 초기화하지 않는다. 3회 후에도 해결되지 않으면 중단하고 원인·시도 내용·남은 차단 요인을 보고한다. 테스트가 승인된 요구사항과 충돌하는 경우를 제외하고 기대값을 바꾸지 않으며, 검사를 생략하거나 약화해 통과시키지 않는다.
8. 변경 파일·동작, 실행 명령과 결과, 미실행 검사·남은 제약을 보고한다. 실행하지 않은 테스트를 성공으로 보고하지 않는다.
9. 최종 보고와 일치하도록 TASKS.md 상태와 검증 근거를 반영한다. 구현과 필수 검증을 모두 마친 작업만 DONE으로 표시한다.
