# UX 리뷰 루프

## 적용과 책임

- 승인된 UI 구현의 의미 있는 작업 단위가 끝나면 실행한다. 파일 저장마다 실행하지 않는다. 단순 문구·링크 변경은 해당 행동과 인접 영역만 검토한다.
- 메인은 구현·수정·테스트, 독립 UX sub-agent 한 명과 UI sub-agent 한 명은 문제 발견·재검증을 맡는다. 이 스킬은 리뷰 위임을 명시적으로 요구한다. 리뷰어는 코드 수정이나 추가 sub-agent 생성을 하지 않는다.
- 새 작업의 최초 리뷰에는 새 컨텍스트를 사용한다(지원 도구에서는 `fork_turns="none"`). 구현 대화 전체나 이전 작업의 ‘문제 없음’ 결론을 넘기지 않는다. 같은 작업의 수정 검증에는 같은 리뷰어를 재사용하고 회차를 초기화하지 않는다. 새 컨텍스트가 불가능하면 그 한계를 기록한다.
- UX 리뷰어는 [ux-designer](../ux-designer/SKILL.md)의 관점을 적용한다. 사용자가 확정한 배치·기능과 구현자의 선택을 구분한다. 확정 요구사항의 불편도 근거를 들어 제안할 수 있지만 자동으로 뒤집지 않는다.
- 이 절차는 메인 에이전트가 실행한다. 백그라운드 자동 실행이나 Hook의 강제 게이트가 아니다. 에이전트 도구가 없으면 독립 리뷰 미실행으로 보고한다.

## 리뷰 준비

매번 [리뷰 요청·기록 형식](references/review-contract.md)을 읽어 요청과 결과 기록에 사용한다.

1. 대상 사용자·방문 목적·진입 경로·성공 행동을 먼저 전달한다. 사용자 연구가 없는 페르소나는 검토용 가설로 표시한다. 예: ‘처음 방문해 공개 퀴즈 하나를 골라 풀려는 비로그인 개발자’. 디자이너 역할과 사용자의 페르소나를 혼동하지 않는다.
2. 확정 제약, 미결정 정책, 미구현 자리 표시자, 수정 가능한 파일·범위를 분리해 전달한다. 구현 순서가 곧 최선의 정보 순서라는 설명을 하지 않는다.
3. 워크트리·커밋/미커밋 diff·실제 경로·데모 상태·격리된 서버 URL과 포트·화면 확인 수단을 제공한다. ‘구현이 명확하다’, ‘잘 배치됐다’, ‘테스트가 통과했으니 문제 없다’처럼 결론을 유도하지 않는다. 요청 문구는 ‘이 화면에서 사용자 목적 달성을 방해하는 문제를 목록화하라’로 시작한다.
4. 리뷰어에게 넘기기 전에 구현자가 Playwright MCP(`.mcp.json`·`.codex/config.toml`에 등록)로 변경 화면을 먼저 열어 명백한 깨짐·콘솔 오류를 정리한다. 이 확인은 리뷰어의 최초 판단을 대신하거나 유도하지 않으며 결과를 '문제 없음' 근거로 전달하지 않는다. 직접 브라우저 조작이 가능하면 리뷰가 끝날 때까지 해당 워크트리 서버를 유지한다. 불가능하면 최신 데스크톱·모바일 캡처와 관찰 가능한 조작 증거를 제공한다. 전체 페이지 캡처에는 viewport 크기도 기록해 첫 화면과 스크롤 아래 영역을 구분한다. 핵심 로그인/소유자 상태를 게스트 캡처로 대신하지 않는다.

## 리뷰 방법

- 먼저 화면만 보고 ‘누구의 어떤 화면인가, 다음에 무엇을 할 수 있는가’를 적는다. 그 뒤 코드·테스트로 원인과 동작을 확인한다. 기존 테스트 통과 여부는 최초 UX 판단의 근거가 아니다.
- 주요 행동 한 개 이상을 진입부터 완료/다음 이동까지 추적한다. 직접 수행, 제공된 조작 증거로 확인, 확인 불가를 구분한다. 클릭 횟수·스크롤·문구 해석·상태 전환 중 어디에서 마찰이 발생하는지 설명한다.
- 다음 관점을 해당 범위에서 각각 평가한다: ① 목적/대상 식별 ② 정보 우선순위와 첫 화면 ③ 핵심 행동의 발견·이동 단계 ④ 불필요한 요소·중복·시각적 밀도 ⑤ 상태/피드백 ⑥ 모바일/키보드 접근성 ⑦ 방문자·본인·타인별 행동.
- 버그가 없어도 주 행동이 묻히거나 불필요한 경유가 있으면 UX 문제 후보로 평가한다. 사용자 영향이 설명되지 않는 취향을 결함으로 만들지 않는다. 발견한 문제에는 최소 변경안과 확인 가능한 해결 조건을 붙인다. 고정된 문제 개수는 요구하지 않는다.
- 문제 없음도 위 관점별 구체적 관찰 근거가 필요하다. 관련 없는 관점은 이유와 함께 해당 없음, 보지 못한 상태는 확인 불가로 표시한다. ‘잘림 없음’, ‘E2E 통과’, ‘요구한 순서와 일치’만으로 정보 구조까지 양호하다고 판정하지 않는다.

## 목록 → 수정 → 재검증

1. 최초 리뷰 R0: 문제 ID·위치/상태·관찰 근거·사용자 영향·우선순위·개선안·해결 조건을 작성한다. 관찰 사실과 가설을 분리한다. 차단/중대, 일반 사용성 문제, 선택적 개선을 구분한다.
2. 메인은 각 문제에 수정·보류·기각과 이유를 기록한다. 승인된 범위 안의 유효한 사용성 문제를 수정한다. 제품 정책·다른 작업자 소유 변경은 보류하고, 필요한 질문과 독립 작업을 구분한다. 리뷰가 새 기능 구현을 자동 승인하지 않는다.
3. 수정 C1 후 구현자가 Playwright MCP로 해당 화면의 해결 조건을 먼저 확인하고, 같은 리뷰어가 R1을 수행한다. 변경 화면과 근거, 이전 문제 목록을 제공한다. 해결 조건을 재확인하고 새 회귀도 살핀다. C2/R2, C3/R3까지 허용한다. 최초 리뷰 포함 최대 4회 리뷰이며, 세 번째 수정 후에도 재검증은 필수다.
4. 회차 기록은 `docs/ux-reviews/<TASK_ID>.md` 한 파일에 유지한다. 최초 리뷰·전체 문제 목록·수정/보류/기각 이유·각 재검증 결과·최종 한계를 남기고 TASKS에서 연결한다. 사용자 피드백으로 수정한 내용을 sub-agent가 발견한 문제로 기록하지 않는다.

## 종료와 완료 보고

- 조기 종료는 필수 미해결 문제 없음, 일반 문제의 처리 근거, 관련 평가 관점의 근거, 핵심 상태 확인을 모두 검토한 뒤 결정한다. 문제를 만들거나 3회를 억지로 채우지 않는다.
- 문제 목록이 없거나 ‘문제 없음’의 근거가 빠졌으면 리뷰 결과를 보완 요청한다. 핵심 화면/동작을 확인할 수 없으면 해당 범위 검증 미완료로 기록하며 UX 통과로 바꾸지 않는다. 최대 회차 소진·같은 문제의 반복·도구 차단은 남은 문제와 함께 보고한다.
- 마지막 코드 변경 후 [변경 범위별 검증·실패 처리](../implement-feature/references/verification.md)를 따른다. 테스트 성공은 UX 판단을 대신하지 않고, UX 리뷰는 테스트·전체 코드 리뷰를 대신하지 않는다.
- 완료 전에 메인은 기록 파일의 회차·문제 처리·최종 확인 근거를 확인한다. 최종 보고에는 실제 수정 횟수, 직접/간접 확인 범위, 미해결/보류/미확인 사항을 적는다. push·PR·병합 권한은 별도 사용자 요청을 따른다.

## UI 리뷰 통합

- UI 리뷰어는 [ui-designer](../ui-designer/SKILL.md)를 적용한다. 각 역할의 최초 리뷰는 새 컨텍스트를 사용하고 재검증에는 각 리뷰어를 재사용한다.
- 두 리뷰어에게 같은 화면 증거와 확정 제약을 제공한다. UI 리뷰어는 흐름 추적 대신 시각적 위계·타이포그래피·여백·색상·정렬·비례·일관성·모바일 구성을 평가한다.
- 메인은 두 목록을 통합한다. 충돌 시 확정 요구사항과 접근성을 우선하며 남는 시각적 선택은 근거와 함께 결정한다.
- 수정 C1~C3은 두 역할을 합친 공통 회차다. 각 회차에서 두 리뷰어가 관련 해결 조건과 회귀를 재확인한다. 역할마다 횟수를 초기화하지 않는다.
- 같은 기록 파일에 역할별 관찰·문제·재검증과 미확인 한계를 남긴다. 문서·백엔드 전용 작업에서는 화면 리뷰를 시작하지 않는다.
