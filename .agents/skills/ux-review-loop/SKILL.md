# UX 리뷰 루프

## 시작과 역할

- 승인된 UI 구현에서 화면·흐름·인터랙션의 의미 있는 작업 단위가 완성되면 실행한다. 렌더링·파일 저장마다 실행하지 않는다. 문구·스타일도 사용성에 영향을 주면 변경 규모에 맞춰 검토한다.
- 메인 에이전트는 구현·수정·테스트를 맡고, 별도 UX 리뷰 sub-agent 하나를 생성해 실제 화면 검증을 맡긴다. 이 스킬은 해당 범위의 sub-agent 위임을 명시적으로 요구한다. 리뷰어는 코드를 수정하거나 다른 sub-agent를 생성하지 않는다.
- 사용 가능한 에이전트 생성 도구를 사용한다. 가능하면 새 컨텍스트에 대상과 근거를 전달하고 이후 같은 리뷰어를 재사용한다. 특정 모델을 강제하지 않는다. 도구가 없으면 독립 리뷰 미실행으로 보고하고 셀프 리뷰를 독립 검증으로 표시하지 않는다.
- 이 스킬은 실행 중인 작업의 절차다. 세션 종료 후 자동 재실행하는 백그라운드 루프나 런타임 권한 설정이 아니다.

## 리뷰어에게 전달할 내용

- [ux-designer](../ux-designer/SKILL.md), 관련 PRD REQ/AC와 페이지 구조, 요청 범위·제외 영역·파일 소유권.
- 대상 워크트리·변경 파일·현재 코드 식별 정보, 해당 워크트리 전용 서버 URL·포트, 접근 가능한 경로와 데모 사용자·상태 재현 방법.
- 최신 데스크톱·모바일 화면과 필요한 브라우저 조작 수단. 직접 브라우저를 사용할 수 없다면 메인이 촬영한 최신 스크린샷·조작 결과를 제공하고 간접 검토임을 기록한다. 정적 캡처만으로 키보드·동작 검증을 통과했다고 하지 않는다.
- 이전 회차의 문제 ID·수정 내역·미해결 사유. 구현자의 자체 평가는 검증 근거를 대신하지 않는다.

리뷰어는 실제로 확인한 범위 안에서 핵심 행동, 정보 순서, 로딩·빈 상태·오류·완료, 모바일·키보드 접근성, 방문자/사용자 차이, 디자인 시스템·요구사항 준수를 확인한다. 테스트용 조작은 격리된 더미 상태에서 수행하고 다른 워크스페이스 서버·데이터는 변경하지 않는다.

## 문제 목록과 반복

1. 최초 리뷰를 실시한다. 문제마다 ID, 위치·상태, 관찰 근거 또는 재현 절차, 사용자 영향, 우선순위, 개선안, 해결 확인 조건을 기록한다. 핵심 행동 차단·요구사항 위반·중대한 혼동·접근성 문제와 선택적 개선을 구분한다. 근거 없는 취향을 결함으로 만들거나 일정 개수의 문제를 강제하지 않는다.
2. 메인은 범위 내 유효한 문제를 수정하고 관련 테스트를 실행한다. 제품 정책·API 계약·타인 소유 파일 변경이 필요하면 해당 문제를 보류해 조율한다. 리뷰 의견을 기각할 때는 근거를 남긴다. 리뷰 결과가 새로운 기능을 자동 승인하지 않는다.
3. 리뷰어가 최신 화면에서 해결 여부와 회귀를 확인한다. 한 회차는 ‘수정 + 재검증’이다. 최초 리뷰 후 최대 3회 수정하며, 마지막 수정도 반드시 재검증한다. 최초 리뷰 포함 최대 4회의 리뷰이고 네 번째 수정은 자동 실행하지 않는다.
4. 중대한 미해결 문제가 없고 필요한 화면 확인·관련 검사가 통과하면 조기 종료한다. 선택적 개선은 별도로 남길 수 있다. 같은 문제가 진전 없이 반복되거나 도구·정책·소유권 문제로 진행할 수 없으면 해당 부분을 중단하고 근거와 남은 항목을 보고한다.

같은 작업의 회차를 에이전트 교체·재시작·문제 이름 변경으로 초기화하지 않는다. 작업 메모에 수정 회차·문제 상태·근거 위치를 유지한다. 기존 [검증 실패 처리](../implement-feature/references/verification.md)의 재시도 한도도 유지하며, 그 한도에 도달하면 UX 회차가 남아 있어도 우회하지 않는다.

## 종료와 보고

- 마지막 코드 변경 후 기존 구현 절차의 전체 검증을 수행한다. 테스트를 고친 뒤 화면 동작이 달라지면 남은 회차 안에서 다시 리뷰한다. 한도 소진 후 수정이 필요하면 미완료 항목으로 보고한다.
- 수정 횟수, 실제 화면 확인 범위·방법, 해결·미해결·보류 문제와 테스트 결과를 보고한다. 화면 확인 불가나 중대한 문제를 남기고 UX 검증 완료로 표시하지 않는다.
- 이 리뷰는 실제 사용자 연구나 전체 코드 리뷰·보안 검증을 대신하지 않는다. push·PR·병합은 별도 사용자 요청 범위를 따르고 최종 병합 결정은 사용자에게 둔다.
