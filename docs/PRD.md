# Bugri 제품 요구사항

## 1. 문서 목적과 제품 방향

Bugri는 개발자가 학습한 지식과 코드를 퀴즈로 바꾸고, 검토하고, 반복해서 풀 수 있는 개발자 학습 플랫폼이다. 버그리는 학습 과정에 짧은 반응을 제공하는 캐릭터다.

전체 제품은 퀴즈 제작·관리·풀이뿐 아니라 퀴즈 공유, 친구와 함께하는 학습, 관심 퀴즈와 콘텐츠 구독으로 확장한다. 기존 README와 홈 화면에 있는 이 방향은 유지한다. 이번 MVP에서 제외하는 기능은 폐기하는 것이 아니라 후속 범위로 남긴다. 구독의 과금 여부와 상세 정책은 아직 정하지 않는다.

이 문서는 사용자 요구사항과 수용 기준의 기준점이다. 구현 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 진행 상태는 [TASKS.md](TASKS.md)를 따른다. 아래 내용은 구현 계획이며 현재 기능이 구현되었다는 뜻이 아니다.

## 전체 제품 요구사항 — 확정된 장기 방향

아래 A~F는 확정된 제품 요구사항이다. 구현 시기와 세부 운영 정책은 별도 결정하며, 아래 MVP 범위에 명시된 부분만 이번에 구현한다.

| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. AI 퀴즈             | 개발자의 지식·코드로 질문·선택지·정답·해설·태그 생성, 작성자 검토·수정, 본문·해설의 언어 지정 코드 블록, 코드 문제점 찾기·실행 결과 예측, 비공개 저장·공개, 문제별 오답 복습·학습 기록. MVP는 단일 정답 4지선다형이며 OX·복수 정답·코드 직접 수정은 후속 기능 |

| D. 버그리 데스크테리어 | 학습 보상 DP, DP로 가상 아이템 구매, 키보드·모니터·책상·소품·배경 카테고리, 구매 보관함, 장착·해제, 내 데스크 꾸미기·다른 사용자 데스크 구경. 중복 보상·중복 구매·잔액 초과 구매 방지                                                                         |
| E. 마이페이지          | 닉네임·프로필 이미지, Markdown 자기소개, GitHub·외부 기술 블로그 링크, 출제 퀴즈 목록, 주요 학습 태그, 구독 관리, 학습 성과, 대표 퀴즈 고정, 데스크테리어 공개                                                                                                |
| F. 장기 확장           | 기술 블로그 작성, 블로그 글에 퀴즈 삽입, 외부 블로그에 퀴즈 임베드                                                                                                                                                                                            |

## 2. 이번 MVP 범위

| 포함                             | 후속 제품 범위 또는 이번에 구현하지 않을 항목 |
| -------------------------------- | --------------------------------------------- |
| 지식 및 코드 텍스트 입력         | 파일 업로드, URL 수집, 저장소 연동            |
| 입력을 기반으로 한 AI 퀴즈 생성  | 여러 AI 모델 선택, 자동 대량 생성             |
| 문제·보기·정답·해설 검토 및 수정 | 공동 편집, 자동 승인                          |
| 초안 저장 및 검토 완료 퀴즈 저장 | 공개 공유, 검색·탐색, 친구·커뮤니티           |
| 저장한 퀴즈 풀이와 결과 확인     | 추천, 오답 노트, 장기 통계, 복습 알림         |
| 버그리 기본 반응                 | 성장·경험치·아이템·상점·대화형 캐릭터         |
| 같은 사용자의 저장 목록 조회     | 구독, 결제, 회원가입·소셜 로그인 화면         |

태그 자동 생성·관리, 공개 설정, 오답 복습 제품 기능, XP·DP, 쇼핑몰·데스크테리어, 미션·Streak·업적, 마이페이지·블로그·임베드는 이번 MVP에 포함하지 않는다. 풀이 진행 복원과 결과 저장은 장기 학습 통계 기능과 구분한다. 코드 문제점 찾기·실행 결과 예측은 기존 4지선다형 안에서 출제할 수 있으며 실제 실행으로 채점하지 않는다.

## 3. MVP 설계 가정

사용자가 지정한 여섯 가지 기능 외의 세부사항은 다음과 같이 제안한다. 변경이 필요하면 구현 전에 이 문서와 API 계약을 함께 갱신한다.

- 확정: 퀴즈 하나는 문항 여러 개로 구성하며 MVP 문항 유형은 단일 정답 4지선다형이다. 아래 수치·저장 정책은 구현 전 확인할 설계 제안이다.
- 코드 블록 단순안: 문항 본문과 해설에 각각 선택적으로 1개를 지원한다. 각 블록은 언어와 코드 내용(최대 10,000자)을 가지며 줄바꿈·들여쓰기를 보존한다. 임의 위치의 여러 블록과 리치 텍스트 편집은 후속 설계다.
- 생성 문항 수는 1~5개이며 기본값은 3개다. 난이도 선택은 이번 범위에서 제외한다.
- 지식과 코드 중 하나 이상을 입력한다. 각각 최대 10,000자이며 공백만 있는 입력은 인정하지 않는다. 코드 언어는 선택 입력이다.
- 제목은 1~100자, 문제와 해설은 각각 1~2,000자, 보기는 각각 1~500자다. 한글·영문을 지원하며 길이는 유니코드 코드 포인트 기준이다.
- 로그인 기능 대신 서버가 발급한 익명 세션으로 소유자를 식별한다. 같은 브라우저의 유효한 세션에서 저장 내용을 다시 볼 수 있다. 다른 기기 간 동기화와 세션 삭제 후 복구는 제공하지 않으며 이를 안내한다.
- 검토 완료 저장은 본인에게 풀이를 허용하는 승인이다. 공개 게시나 다른 사용자에게 공유하는 행위가 아니다.
- 승인 저장한 READY 퀴즈는 MVP에서 수정하지 않는다. 저장된 DRAFT는 계속 수정할 수 있다. READY를 다시 만들려면 새 퀴즈를 생성한다. 사용자 삭제·보관함 화면은 후속 범위이며 운영 데이터 삭제 정책과 구분한다.

## 4. 핵심 사용자 여정

1. 사용자가 공부한 지식이나 코드 조각을 입력한다.
2. 생성할 문항 수를 정하고 AI 퀴즈 생성을 요청한다.
3. 생성된 초안에서 문제, 보기, 정답, 해설을 읽고 필요한 내용을 수정한다.
4. 초안을 저장해 나중에 이어서 검토하거나, 모든 문항의 검토를 확인하고 승인 저장한다.
5. 저장 목록에서 승인된 퀴즈를 골라 문항별로 답을 제출한다.
6. 제출한 문항의 정답·해설과 버그리 반응을 확인한다.
7. 마지막 문항까지 풀면 정답 수를 확인하고 다시 풀 수 있다.

## 5. 상세 요구사항과 수용 기준

### REQ-01 지식과 코드 입력

사용자는 지식과 코드를 별도 입력 영역에 붙여넣을 수 있다. 코드의 줄바꿈과 들여쓰기는 보존하며 코드 실행은 제공하지 않는다. 입력 내용이 AI 제공자에게 전송됨을 생성 전에 안내하고, 비밀키나 개인정보를 넣지 않도록 짧게 안내한다.

수용 기준:

- AC-01a: 지식만, 코드만, 둘 다 입력한 경우 각각 생성 요청이 가능하다. 두 영역 모두 비어 있거나 공백뿐이면 요청을 차단하고 이유를 표시한다.
- AC-01b: 길이·문항 수 제한 위반을 해당 입력 옆에 표시하고 서버에서도 동일하게 검증한다. 입력 오류가 나도 작성 내용이 남는다.
- AC-01c: 코드의 줄바꿈을 유지하고 HTML·스크립트 문자열은 텍스트로 표시한다. 입력 코드를 브라우저나 서버에서 실행하지 않는다.

### REQ-02 AI 퀴즈 생성

사용자는 입력에 근거한 문제·보기·정답·해설을 초안으로 받는다. AI 출력에는 오류가 있을 수 있으므로 검토가 필요하다는 표시를 유지한다.

수용 기준:

- AC-02a: 생성 중임을 표시하고 같은 화면의 중복 클릭을 막는다. 성공하면 요청한 개수의 문항과 문항별 보기 4개, 정답 1개, 해설을 보여준다.
- AC-02b: 출력 구조가 잘못되었거나 정답이 보기에 없거나 문항 수가 다르면 성공으로 처리하지 않는다. 오류와 재시도 방법을 보여주고 원래 입력을 유지한다.
- AC-02c: 입력이 부족해 생성할 수 없거나 제공자 오류·시간 초과가 발생하면 사용자에게 이해 가능한 안내를 표시한다. 승인된 퀴즈를 만들거나 기존 초안을 덮어쓰지 않는다.
- AC-02d: 정상 생성 결과는 서버에 DRAFT로 저장된다. 새로고침 후 저장 목록에서 다시 열 수 있다. AI 호출에 성공했어도 DB 저장에 실패하면 저장 성공으로 표시하지 않는다.
- AC-02e: 입력 안의 명령문을 시스템 지시로 따르지 않도록 처리한다. 생성 성공이 내용의 정확성을 보증하지 않으며 사용자 승인을 생략하지 않는다.
- AC-02f: 코드가 필요한 문항은 본문·해설 코드 블록의 언어와 내용을 구조 검증하고 DRAFT로 저장한다. 코드 없는 문항도 허용한다. 기술적 정답 여부는 작성자가 검토하며 사용자 코드와 생성 코드를 실행하지 않는다.

### REQ-03 정답·해설 검토 및 수정

작성자는 원본 입력과 초안을 함께 확인하고 제목, 문제, 보기, 정답, 해설을 수정할 수 있다. 검토 화면은 정답을 볼 수 있는 작성자 전용 화면이다.

수용 기준:

- AC-03a: 모든 문항의 정답과 해설을 확인·수정할 수 있다. 각 문항에서 정답은 정확히 하나만 선택한다.
- AC-03b: 필수값 누락, 빈 보기, 동일 문항 내 중복 보기, 유효하지 않은 정답은 저장을 막고 해당 위치에 안내한다. 보기 중복은 앞뒤 공백 제거 후 비교한다.
- AC-03c: 각 문항에 검토 완료를 명시적으로 표시한다. 문항 내용을 수정하면 해당 문항의 검토 완료 표시가 해제된다.
- AC-03d: 모든 문항을 검토하지 않은 상태에서는 승인 저장할 수 없다. 서버도 검토 완료 상태와 내용을 검증한다.
- AC-03e: 저장하지 않은 변경이 있으면 화면 내 이동 시 알리고, 브라우저 종료·새로고침 경고는 브라우저가 지원하는 범위에서 제공한다. 자동 복구를 보장하지 않는다.
- AC-03f: 본문·해설 코드 블록과 언어를 편집·제거할 수 있고 저장·재조회 후 줄바꿈과 들여쓰기가 유지된다. 코드 변경도 검토 완료를 해제한다. 내용 저장 성공 → 저장된 내용 재확인 → 명시적 검토 완료 저장 → 최종 승인 순서를 따른다. 내용 수정과 검토 완료를 한 요청으로 처리하지 않는다.

### REQ-04 퀴즈 저장과 목록

사용자는 수정한 초안을 명시적으로 저장하거나 검토를 완료한 뒤 풀이 가능한 상태로 저장한다. 저장 목록에는 제목, 상태, 문항 수, 최종 저장 시각을 표시한다.

수용 기준:

- AC-04a: 초안 저장은 DRAFT를 유지한다. 승인 저장은 검증을 통과한 최신 내용 전체를 READY로 바꾸고, 성공 응답 후에만 완료를 알린다.
- AC-04b: 저장 후 다시 열거나 서버를 재시작해도 마지막으로 성공한 저장 내용이 유지된다. 실패 시 수정 내용을 화면에 유지하고 재시도를 제공한다.
- AC-04c: 저장 목록에서 DRAFT는 검토 화면, READY는 풀이 시작으로 연결한다. 빈 목록에는 생성 화면으로 가는 안내를 표시한다.
- AC-04d: 중복 저장 요청으로 퀴즈가 복제되지 않는다. 여러 탭에서 오래된 내용으로 저장하면 충돌을 알리고 최신 내용을 다시 확인하게 한다.
- AC-04e: 다른 세션 소유자의 퀴즈 목록·초안·정답·풀이 기록에 접근할 수 없다.
- AC-04f: 세션 만료·쿠키 삭제 시 기존 데이터에 접근할 수 없음을 안내한다. 접근 만료가 즉시 데이터 삭제를 뜻하지 않으며, 보존 기간·삭제 시점은 운영 전 확정하여 안내한다. 새 익명 세션에 이전 데이터를 자동 연결하지 않는다.

### REQ-05 퀴즈 풀이

사용자는 READY 퀴즈를 한 문항씩 풀고 제출한 문항의 결과를 확인한다. 채점은 승인 저장된 정답을 기준으로 서버에서 수행한다.

수용 기준:

- AC-05a: DRAFT는 직접 URL이나 API 호출로도 풀이를 시작할 수 없다. 새 풀이를 시작하면 문항 수와 현재 진행 위치를 표시한다.
- AC-05b: 답을 고르기 전에는 제출할 수 없다. 제출 전에는 풀이 화면, HTML, 클라이언트 상태 및 풀이 API 응답에 정답·해설·정오 표시를 포함하지 않는다. 작성자가 이전에 본 정답까지 잊게 하는 것은 요구하지 않는다.
- AC-05c: 제출 후 선택 답, 정오, 정답, 해설을 보여준다. 미제출 문항의 정답은 함께 반환하지 않는다.
- AC-05d: 한 풀이에서 같은 문항을 반복 제출해도 최초 결과와 점수가 유지된다. 다른 답으로 변경 제출하면 거부하고, 정답은 클라이언트가 보내지 않는다.
- AC-05e: 제출 실패 시 선택한 답을 유지하고 재시도를 허용한다. 새로고침 후 같은 풀이의 제출 결과와 다음 진행 위치를 복원한다.
- AC-05f: 모두 제출하면 정답 수/전체 문항 수를 보여준다. 다시 풀기는 별도 풀이를 만들어 시작하며 이전 기록을 덮어쓰지 않는다.
- AC-05g: 본문 코드 블록은 풀이 중 표시하고 해설 코드 블록은 해당 문항 제출 후에만 표시한다. 언어·줄바꿈·들여쓰기를 보존하고 실행 버튼이나 코드 실행 채점을 제공하지 않는다.

### REQ-06 버그리 기본 반응

버그리는 추가 AI 호출 없이 미리 정의한 표정·짧은 문구로 학습을 돕는다. 사용자가 정답 여부를 캐릭터에만 의존하지 않도록 텍스트 결과도 제공한다.

| 상황           | 반응 예시                                     |
| -------------- | --------------------------------------------- |
| 대기           | 기본 표정, “배운 내용을 퀴즈로 바꿔볼까?”     |
| 생성 중        | 기다리는 표정, “문제를 만들고 있어!”          |
| 초안 생성 성공 | 반가운 표정, “정답과 해설을 함께 확인해줘.”   |
| 정답           | 기쁜 표정, “잘했어!”                          |
| 오답           | 격려하는 표정, “해설을 읽고 다시 도전해보자.” |
| 풀이 완료      | 축하하는 표정, “끝까지 풀었어!”               |
| 요청 실패      | 기본 표정, “다시 시도해보자.”                 |

수용 기준:

- AC-06a: 각 상황에 맞는 반응을 표시한다. 정오 반응은 서버 채점 성공 이후에만 바뀐다.
- AC-06b: 마지막 문항에서는 정오 반응을 먼저 보여주고 결과 화면으로 이동할 때 완료 반응을 보여준다.
- AC-06c: 캐릭터 이미지가 로드되지 않거나 애니메이션을 줄이는 설정에서도 텍스트 안내와 핵심 흐름을 사용할 수 있다. 오답에 비난하는 문구를 사용하지 않는다.

## 6. 공통 품질과 출시 기준

- 주요 화면은 모바일과 데스크톱에서 입력·검토·풀이가 가능하고 키보드로 모든 핵심 동작을 수행할 수 있어야 한다. 입력 레이블, 오류 설명, 요청 진행 상태를 제공한다.
- 원본 코드, 정답, AI 키, 세션 토큰을 일반 로그에 남기지 않는다. AI 키와 DB 접속 정보는 서버에서만 사용한다.
- AI 요청에 시간 제한과 세션별 요청 제한을 적용한다. 무한 재시도하지 않고 제한에 도달하면 사용자에게 알린다. 구체적인 운영 값은 ARCHITECTURE.md에 정의한다.
- MVP 완료는 여섯 요구사항의 수용 기준을 모두 충족하고, 실제 MySQL 저장과 AI 연동을 포함한 핵심 여정이 검증된 상태다. 화면만 있거나 모의 응답만으로 작동하는 상태는 완료가 아니다.
- 공유·구독 등 후속 기능의 구현이나 성과 지표 수집을 MVP 완료 조건에 추가하지 않는다.

## 7. 후속 결정 사항

확정 스택은 Next.js 16 App Router, React 19, TypeScript, 초기 Next.js Route Handlers, MySQL 8.4, 외부 LLM API, Codex다. Docker·Kubernetes는 배포 학습 대상이며 MVP 기능 개발의 선행 조건이 아니다. 향후 Spring Boot 전환을 위해 HTTP 계약을 분리한다.

AI 제공자·모델, ORM/DB 접근 라이브러리, 인증 라이브러리, 테스트 도구, 실제 배포 환경, 세션 TTL과 익명 데이터 보존·삭제 기간은 미결정이다. 세부 정책은 ARCHITECTURE.md의 제안을 검토해 관련 구현 전에 확정한다. 회원가입·결제는 선행 구현하지 않는다.
