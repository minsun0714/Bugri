# Bugri 제품 요구사항

## 1. 문서 목적과 제품 방향

Bugri는 개발자가 배운 내용을 한 곳에 적으면 LLM이 이를 퀴즈로 바꿔 주는 학습 플랫폼이다. 학습 내용에는 코드 블록을 넣을 수 있다. 작성자는 결과가 마음에 들지 않으면 추가 프롬프트로 다시 생성하고, 검토 후 공개한다. 버그리는 학습 과정에 짧은 반응을 제공하는 캐릭터다.

전체 제품은 퀴즈 제작·관리·풀이뿐 아니라 퀴즈 공유, 친구와 함께하는 학습, 사용자·해시태그 구독으로 확장한다. 구독 대상은 사용자, 해시태그 또는 사용자와 해시태그의 조합이다. 퀴즈는 구독 조건에 따라 제공되는 학습 콘텐츠이며 구독 대상이 아니다. 블로그 글 등 다른 콘텐츠 제공은 구독 요구사항에 포함하지 않는다. 1단계에서 제외하는 제품 기능도 이 문서에 남긴다.

이 문서는 사용자 요구사항과 수용 기준의 기준점이다. 구현 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 진행 상태는 [TASKS.md](TASKS.md)를 따른다. 아래 내용은 구현 계획이며 현재 기능이 구현되었다는 뜻이 아니다.

| 상점      | BugCoin 상품 조회→구매→보관함→장착 UX. 잔액 부족·중복 요청을 화면과 Mock API에서 재현                | 실제 BugCoin 잔액 차감·구매·보관함 추가를 MySQL 트랜잭션으로 처리하고 동시 요청을 제어    |
| 상태 보존 | Mock 파일 초기 데이터 + 더미 사용자별 localStorage 변경 상태. 브라우저 삭제·기기 변경 시 유실 가능   | MySQL 영속화와 서버 검증                                                                  |

1단계에는 DB를 연결하지 않고 MySQL·Prisma·mysql2를 설치하지 않는다. Mock 인증과 더미 사용자는 화면 검증용이며 실제 보안 기능으로 간주하지 않는다. 1단계에서도 API 요청·응답 타입을 정의하고 UI가 더미 데이터에 직접 종속되지 않게 한다. 1단계 Vercel 배포는 프로토타입 배포이며 실제 Google 로그인·DB·거래 안전성의 검증 근거가 아니다. 구독 피드·무한 스크롤·구독자의 구독자 기반 추천·인기 퀴즈 자동 추천·구독과 무관한 기본 퀴즈는 로그인 사용자 홈에서 제외한다. 비로그인 홈의 랜덤 체험은 AC-05h의 예외를 적용한다. PG·현금 결제는 제품 범위에 포함하지 않는다.

상점의 전체 제품 요구사항인 관리자 직접 상품 등록, 구매·보관함·장착과 다른 사용자 데스크 조회는 유지한다. 1단계는 요청된 상점 구매·장착 UX와 이를 보여 줄 더미 상품을 제공하며, 실제 관리자 권한·등록 API·거래 보장은 2단계에서 구현한다. 다른 제품 요구사항도 이 문서에 남기되 1단계 완료 조건에 임의로 추가하지 않는다.

1단계 초기 데이터는 프로젝트의 Mock 파일에서 읽는다. 퀴즈 생성·수정·soft delete, 구독·해제, 풀이 기록, BugCoin 구매·장착 및 사용자 설정의 변경은 더미 사용자별 localStorage에 저장하고 재접속 시 복원한다. UI는 타입이 정의된 API 클라이언트와 Mock 어댑터만 사용한다. 로컬에서 초기 파일은 수정할 수 있지만 배포된 파일은 읽기 전용이며 Vercel 서버 파일이나 서버 메모리를 사용자 변경의 영속 저장소로 쓰지 않는다.

## 3. 제품 규칙과 단계별 적용

아래 제품 규칙을 1단계에는 Mock API·화면에 적용하고, 영속성·실제 권한·동시성 보장은 2단계에서 적용한다. 세부 정책이 바뀌면 API 계약도 함께 갱신한다.

- 확정: 사용자는 배운 내용을 한 입력란에 적고, 코드가 필요하면 같은 내용 안에 코드 블록을 넣는다. 문제 유형과 퀴즈 수를 사용자가 반드시 지정하게 하지 않는다. 요청당 독립 퀴즈 1~5개와 개별·일괄 저장은 확정 정책이며 구체적인 문제 형식은 구현 전 결정한다.
- 학습 내용의 코드 블록은 같은 입력 안의 필요한 위치에 여러 개 넣을 수 있어야 한다. Markdown의 언어 지정 fenced code block을 초기 표현으로 제안한다. 퀴즈 본문·해설의 코드 표현 방식은 생성 결과 형식과 함께 확정한다.
- LLM은 요청당 독립 퀴즈 1~5개를 만든다. 문제 형식은 구현 전 결정한다. 난이도·퀴즈 수·코드 언어를 필수 입력으로 요구하지 않는다.
- 학습 내용은 하나의 입력값으로 받으며, 코드 블록 표기와 공백을 포함한 전체 길이는 유니코드 코드 포인트 기준 최대 10,000자다. 내용 안의 코드 블록은 언어·줄바꿈·들여쓰기를 보존한다. 공백뿐인 입력은 거부한다.
- 제목·문제·해설의 길이 제한, 생성 가능한 문제 형식과 정답 검증 규칙은 출력 스키마를 정할 때 결정한다. 사용자는 이 값들을 생성 전에 일일이 설정하지 않는다.
- 1단계는 화면 검증용 더미 사용자를 Mock API에 전달하고 실제 인증·권한 보장을 주장하지 않는다. 2단계는 Google OAuth2·JWT와 내부 User ID로 소유권을 검사한다. 익명 OwnerSession 설계는 사용하지 않는다.
- LLM 최초 생성 결과는 작성자에게 후보 퀴즈로 보여준다. 작성자가 개별 퀴즈 또는 전체 퀴즈를 명시적으로 저장하면 PENDING 퀴즈가 된다. 작성자가 내용을 검토한 뒤 공개 범위를 PRIVATE 또는 PUBLIC으로 선택해 승인한다. 승인 후 PRIVATE↔PUBLIC 전환을 허용한다. 생성이나 재생성은 자동 승인·공개하지 않는다. 별도의 CONFIRMED 상태는 두지 않는다.
- PENDING에서는 추가 프롬프트로 다시 생성할 수 있다. 승인된 PRIVATE·PUBLIC도 작성자가 직접 수정하거나 추가 프롬프트로 LLM 재생성할 수 있다. 승인된 퀴즈를 고칠 때는 현재 서비스 중인 버전을 유지하고 별도의 PENDING 수정본을 검토한 뒤 승인해 교체한다. 실패하면 이전 결과와 입력 프롬프트를 유지한다. 공개 범위 전환은 내용 수정과 구분한다.
- 작성자는 자신의 PUBLIC 퀴즈를 PRIVATE로 전환하거나 자신의 퀴즈를 삭제할 수 있다. 비공개·삭제 퀴즈는 구독 기반 학습 대상에서 즉시 제외한다. 타인의 진행 중 답안 제출은 차단하고 이용할 수 없음을 안내한다. 삭제는 soft delete로 처리해 사용자 화면에서 즉시 숨기며, 완료 기록과 이미 획득한 스트릭·XP·BugCoin은 유지한다.
- 홈 학습은 직접 구독 조건에 맞는 PUBLIC 퀴즈를 선택한 태그로 좁혀 한 문제씩 제공한다. 기본 태그는 전체이며 MVP에서는 한 태그만 선택한다. 다음 문제도 같은 태그를 유지한다. 기존 하루 최대 1개·당일 선정 고정 정책은 이 연속 풀이 흐름으로 대체한다. 사용자별 학습 시간대의 하루에 1개 완료하면 연속 학습 조건을 충족한다.

## 4. 전체 제품의 핵심 사용자 여정

1. 사용자가 배운 내용을 한 곳에 적는다. 필요한 곳에 코드 블록을 넣는다.
2. LLM에 퀴즈 생성을 요청한다. 퀴즈 수나 문제 형식 선택은 필수가 아니다.
3. 생성 후보를 개별 또는 일괄 저장해 PENDING 퀴즈로 만들고 검토한다. 마음에 들지 않으면 추가 프롬프트로 다시 생성하거나 직접 수정한다.
4. 만족한 결과의 모든 퀴즈와 각 퀴즈의 최대 3개 해시태그를 확인하고 PRIVATE 또는 PUBLIC으로 승인한다. 이후 공개 범위를 바꿀 수 있다.
5. PRIVATE는 작성자만, PUBLIC은 다른 사용자도 풀 수 있다. 1단계에는 더미 사용자로 이 화면 흐름을 검증하고 2단계에는 인증된 사용자 권한을 적용한다. 홈에서 전체 또는 기술 해시태그 하나를 선택하고, 구독 조건과 태그에 맞는 미풀이 PUBLIC 퀴즈를 한 문제씩 푼다. 없으면 개발자·해시태그 탐색과 구독을 안내한다.
6. 선정한 퀴즈의 답을 제출하고 결과·BugCoin 보상을 확인한다. 완료 후 다음 문제를 제공하며 선택 태그를 유지한다. 미풀이 후보를 소진하면 태그 탐색을 제공하고 완료 문제를 다음 문제로 다시 순환시키지 않는다. BugCoin으로 상점 아이템을 구매하고 내 데스크에 장착할 수 있다.
7. 상점에는 관리자가 상품 정보를 직접 입력해 신규 상품을 등록한다.
8. 다른 사용자의 마이페이지에 들어가면 그 사람이 장착한 데스크가 바로 보인다.
9. 승인된 퀴즈도 수정하거나 LLM에 다시 생성하도록 요청할 수 있고, 필요 없으면 삭제할 수 있다.

## 5. 상세 요구사항과 수용 기준

아래 수용 기준은 전체 제품의 기준이다. 1단계에는 §2에 명시된 UX와 Mock API 계약을 적용한다. 실제 인증·소유권 보안·MySQL 영속성·동시성·거래 원자성이 필요한 기준은 2단계에서 충족한다.

### REQ-01 학습 내용 입력

사용자는 배운 지식을 한 입력란에 자유롭게 적는다. 코드가 필요하면 같은 내용의 원하는 위치에 코드 블록을 넣는다. 생성 전에 퀴즈 수·문제 형식·코드 언어를 필수로 고르게 하지 않는다. 1단계 Mock 응답 사용 여부와 2단계 실제 AI 제공자에게 내용이 전송되는지 안내하고 비밀키·개인정보 입력을 피하도록 알린다.

수용 기준:

- AC-01a: 일반 텍스트, 코드 블록, 둘을 섞은 내용으로 생성할 수 있다. 공백뿐인 입력은 이유를 표시하고 거부한다.
- AC-01b: 코드 블록 표기를 포함한 학습 내용 전체가 유니코드 코드 포인트 기준 10,000자를 넘으면 클라이언트·서버에서 동일하게 거부하고 이유를 표시한다. 오류가 나도 작성한 내용은 남는다.
- AC-01c: 여러 코드 블록의 위치·언어·줄바꿈·들여쓰기를 보존한다. HTML·스크립트 문자열은 텍스트로 표시하며 사용자 코드를 실행하지 않는다.
- AC-01d: 학습 내용 입력 화면에 현재 글자 수와 최대치를 `현재 / 10,000자` 형태로 항상 표시한다. 입력·붙여넣기·삭제할 때 즉시 갱신하며 AC-01b와 같은 유니코드 코드 포인트 기준을 사용한다. 초과 시 숫자와 오류 설명을 함께 보여준다.

### REQ-02 LLM 퀴즈 생성과 프롬프트 재생성

LLM은 학습 내용에 근거한 퀴즈를 만든다. 작성자는 PENDING 결과뿐 아니라 승인된 PRIVATE·PUBLIC 퀴즈도 추가 프롬프트로 다시 생성할 수 있다. 승인된 퀴즈의 재생성 결과는 별도의 PENDING 수정본으로 검토한다. 추가 프롬프트는 해당 퀴즈의 수정 지시이며 다른 사용자의 입력이나 시스템 지시가 아니다.

수용 기준:

- AC-02a: 생성 중 상태를 표시하고 중복 요청을 막는다. 문제 형식·퀴즈 수를 필수로 묻지 않고, LLM이 만든 독립 후보 퀴즈 1~5개와 퀴즈별 제안 해시태그 최대 3개를 보여준다.
- AC-02b: 생성 결과의 퀴즈 개수(1~5개)·형식·문제·정답·해설·코드 블록·퀴즈별 해시태그를 서버에서 검증한다. 지원하지 않거나 잘못된 결과는 성공으로 처리하지 않는다. 구체적인 출력 스키마와 지원 문제 형식은 구현 전에 명시한다.
- AC-02c: 작성자가 추가 프롬프트로 PENDING 퀴즈를 다시 생성할 수 있다. 요청에는 원래 학습 내용, 현재 PENDING 결과, 추가 프롬프트를 사용한다. 성공한 새 결과는 해당 퀴즈 한 개의 PENDING 수정본이며 자동 승인·공개하지 않는다.
- AC-02d: 재생성 실패·Mock/제공자 오류·시간 초과·저장 실패 시 기존 PENDING 결과와 추가 프롬프트를 보존하고 재시도 방법을 보여준다. 이전 결과를 빈 값이나 부분 결과로 덮어쓰지 않는다.
- AC-02e: 최초 생성 성공 결과는 작성자 전용 후보 묶음으로 보존·재조회한다. 내 퀴즈 목록에는 사용자가 명시적으로 저장한 퀴즈만 PENDING으로 나타난다. AI 결과가 정확하다는 보장은 하지 않으며 작성자 확인을 생략하지 않는다.
- AC-02f: 학습 내용과 추가 프롬프트 안의 명령을 상위 시스템 지시로 따르지 않도록 분리한다. 사용자 코드와 생성 코드를 실행하지 않는다.
- AC-02g: PRIVATE·PUBLIC 재생성을 시작하거나 실패해도 현재 서비스 중인 버전은 바뀌지 않는다. 성공한 결과는 작성자 전용 PENDING 수정본으로 저장하며 자동 승인·공개하지 않는다.

생성 화면의 모달 밖에서 학습 내용과 요청을 입력한다. 이 입력의 작성·미리보기는 탭으로 나누지 않고 함께 표시하며 넓은 화면에서는 나란히, 모바일에서는 위아래로 배치한다. “퀴즈 만들기”를 누르면 작업 모달이 열리고 생성한 후보와 버그리 대화를 함께 표시한다. 모달 최초 표시에는 퀴즈와 “바로 공개”, “LLM으로 수정” 동작을 보여준다. 퀴즈 선택은 공통 탭으로 제공한다. 최초에는 퀴즈를 표시하고 제목 오른쪽에 “직접 수정”·“LLM으로 수정” 버튼을 둔다. 직접 수정은 퀴즈 아래에 펼치고, LLM으로 수정은 모달 본문 전체를 대화 화면으로 전환한다. 대화 화면 상단의 “퀴즈로 돌아가기”로 기존 퀴즈 화면을 복원한다. 직접 편집을 확정하지 않아도 수정 영역·대화 화면·퀴즈 탭 사이를 이동할 수 있으며, 퀴즈별 초안을 보관해 돌아왔을 때 복원한다. 반영·취소는 해당 퀴즈 초안에만 적용한다. 미반영 직접 수정 초안과 LLM 요청 초안은 독립적으로 유지하고 어느 쪽이든 마지막으로 성공한 반영 결과를 현재 후보로 사용한다. 미반영 초안이 있는 퀴즈의 저장·공개와 미반영 초안이 포함된 일괄 저장은 막고 페이지 이탈 경고를 유지한다. LLM 요청 초안은 화면 전환으로 지우지 않는다. 임시저장(단일 퀴즈의 PENDING 저장)은 바로 공개와 같은 줄에 같은 버튼 스타일로 표시한다. 현재 작성 UI에는 일괄 저장 버튼과 숨겨진 보조 메뉴를 두지 않는다. 바로 공개와 임시저장은 현재 퀴즈 한 개에만 적용한다. 후보 탭과 완료 영역에는 실제 저장된 퀴즈 상태에 따라 공개됨·임시저장됨·비공개를 표시하며 새로고침에도 복원한다. 일괄 저장 API는 기존 계약으로 유지하되 현재 작성 UI에서 호출하지 않는다. 문제 형식은 한국어로 표시하고 선택지에는 번호를 붙이며 정답·해설은 문제와 구분된 영역에 표시한다. LLM 대화 화면에는 원본 학습 내용, 요청·응답 기록, 현재 퀴즈 제목과 추가 요청 입력창을 표시한다. “바로 공개”는 현재 후보 한 개의 문제·정답·해설·태그를 확인했다는 명시적 조작으로 저장·검토·PUBLIC 승인을 한 번에 처리한다. 이 후보 바로 공개 경로는 별도 저장·검토 화면 이동의 예외이며, 생성 자체는 자동 공개하지 않는다. 미반영 직접 편집이나 추가 요청이 있으면 바로 공개를 막는다. 저장한 퀴즈의 승인·수정본 흐름은 기존 규칙을 유지한다. 선택한 후보에 추가 요청을 보내 결과를 갱신하거나 제목·문제·정답·해설·태그를 직접 수정한다. 직접 수정도 이후 추가 요청의 기준에 포함한다. 생성 후 별도 상세로 자동 이동하지 않는다. 작업 이어가기 기능은 두지 않는다. “퀴즈 만들기”는 같은 학습 내용이어도 매번 새 후보 묶음을 생성하며 이전 대화·미반영 편집을 이어가지 않는다. 생성 실패 시 입력은 보존하고 이전 결과를 새 결과로 표시하지 않는다. 새로고침에서는 해당 URL의 반영된 후보와 요청 기록을 복원한다. 입력 중인 미반영 편집은 페이지 이탈 경고 대상이다. 모바일에서는 작업 모달을 전체 화면으로 표시한다. 퀴즈 화면에서는 모달 전체가 아니라 선택한 퀴즈 본문만 세로로 스크롤하며, 모달 헤더와 퀴즈 선택 탭은 스크롤 위치와 관계없이 계속 보여야 한다. 1단계는 Mock 후보·재생성을 사용하며 실제 LLM 실시간 응답·스트리밍 연결은 하지 않는다. 내 퀴즈 목록·검토·승인·관리는 별도 화면에 두며, 생성 화면에는 더미 사용자 선택을 표시하지 않는다. 저장 전 후보에도 추가 요청을 보낼 수 있다. 원본 학습 내용과 현재 후보를 바탕으로 해당 후보만 갱신하고 요청·응답 기록을 보존한다. 실패 시 기존 후보와 작성 중인 요청을 유지한다. 추가 요청만으로 내 목록에 저장하거나 승인하지 않는다. 저장한 후보의 후속 수정은 검토 화면의 PENDING 수정본 흐름을 따른다.

LLM 대화 화면에서는 모달 헤더와 추가 요청 입력창을 고정하고, 요청·응답이 표시되는 대화 본문만 스크롤한다. 대화 화면에 진입하거나 새 응답이 추가되면 최신 메시지가 보이도록 본문을 맨 아래로 이동한다.

직접 수정 화면에서는 기존 퀴즈 미리보기를 함께 표시하지 않고 제목·문제·정답·해설·태그 편집 폼만 표시한다.

### REQ-03 PENDING 검토 및 수정

작성자는 원래 학습 내용과 저장한 PENDING 퀴즈 또는 승인된 퀴즈의 PENDING 수정본을 함께 확인하고 제목과 해당 퀴즈의 문제·정답·해설·해시태그를 검토·수정할 수 있다. 퀴즈당 해시태그는 최대 3개다. 선택지가 있는 형식이면 선택지도 수정한다. 이 화면은 정답을 볼 수 있는 작성자 전용 화면이다.

수용 기준:

- AC-03a: 해당 퀴즈의 문제·정답·해설·해시태그를 확인·수정할 수 있다. 퀴즈당 해시태그 3개 초과를 서버와 화면에서 거부한다. 지원하는 각 문제 형식의 정답 규칙을 검증한다.
- AC-03b: 필수값 누락, 잘못된 정답, 중복·빈 선택지 등 해당 형식의 오류는 저장을 막고 해당 위치에 안내한다.
- AC-03c: 작성자가 저장된 미리보기에서 `승인`을 명시적으로 누르면 검토 완료 기록과 승인을 순서대로 처리한다. 문제·정답·해설·해시태그를 수정하면 해당 퀴즈의 검토 완료 표시가 해제된다. 원래 학습 내용을 바꾸면 해당 퀴즈의 검토 표시를 해제한다.
- AC-03d: 해당 퀴즈의 검토를 완료하지 않은 상태에서는 PRIVATE 또는 PUBLIC으로 승인할 수 없다. 서버도 검토 상태와 내용을 검증한다.
- AC-03e: 저장하지 않은 변경이 있으면 화면 내 이동 시 알리고, 브라우저 종료·새로고침 경고는 브라우저가 지원하는 범위에서 제공한다. 자동 복구를 보장하지 않는다.
- AC-03f: 본문·해설 코드 블록과 언어를 편집·제거할 수 있고 저장·재조회 후 줄바꿈과 들여쓰기가 유지된다. 코드 변경도 검토 완료를 해제한다. 검토 화면은 저장된 미리보기를 기본으로 보여주고 `직접 수정`을 선택했을 때만 편집 폼을 보여준다. 상세 헤더는 목록 복귀·퀴즈 제목·상태를 함께 표시한다. 편집 폼은 기본 정보·문제 구성·해설·분류로 구분하고 원본 학습 내용은 기본적으로 접는다. 추천 태그는 태그 입력 아래 칩으로 제공한다. 추가 프롬프트 재생성은 `직접 수정`과 같은 수준의 버튼으로 제공하고 입력은 별도 모달에서 받는다. 편집 중에는 변경 상태·취소·수정 저장을 하단 고정 작업 바로 제공하고, 최신 내용 재조회는 보조 아이콘으로 분리하며, 삭제는 비편집 상태의 별도 위험 영역에 둔다. 수정 저장 성공 후 미리보기로 돌아가 저장된 내용을 재확인하며, `승인` 한 번으로 검토 완료 저장과 승인을 순서대로 처리한다. 최초 승인 때 PRIVATE/PUBLIC을 선택하고 수정본 승인 때는 현재 공개 범위를 기본으로 유지한다. 승인된 기존 버전과 PENDING 수정본이 함께 있으면 기존 버전은 기본적으로 접고 비교하기를 선택했을 때만 펼친다.
- AC-03g: 승인된 퀴즈의 직접 수정은 새 PENDING 수정본에 저장한다. 수정본 검토 중에는 기존 PRIVATE·PUBLIC 버전의 내용과 공개 범위가 유지된다.

### REQ-04 상태 전환·저장·목록

최초 생성 후보는 작성자가 개별 또는 일괄 저장할 수 있고, 저장된 퀴즈와 재생성 결과는 PENDING이며 작성자만 검토할 수 있다. 작성자가 모든 내용을 확인하고 PRIVATE 또는 PUBLIC을 선택해 승인한다. 승인 후 공개 범위를 변경할 수 있다. 저장 목록에는 각 독립 퀴즈의 제목, 상태, 최종 저장 시각을 표시한다.

수용 기준:

- AC-04a: PENDING 저장은 상태를 유지한다. 검토를 통과한 최신 내용만 작성자의 명시적 요청으로 PRIVATE 또는 PUBLIC으로 바꾼다. 성공 응답 후에만 완료를 알린다.
- AC-04b: 1단계는 Mock 파일로 초기화하고 더미 사용자별 localStorage 변경 상태를 저장·복원해 저장·재조회 UX를 검증한다. 서버 재시작 이후 영속성은 2단계 MySQL에서 보장한다. 실패 시 수정 내용을 화면에 유지하고 재시도를 제공한다.
- AC-04c: 내 목록에서 PENDING은 검토 화면, PRIVATE는 작성자 풀이, PUBLIC은 공개 퀴즈로 연결한다. 빈 목록에는 생성 화면으로 가는 안내를 표시한다.
- AC-04d: 중복 저장·수정본 승인 요청으로 퀴즈가 복제되거나 오래된 수정본이 최신 내용을 덮어쓰지 않는다. 여러 탭에서 오래된 내용으로 저장하면 충돌을 알리고 최신 내용을 다시 확인하게 한다.
- AC-04e: 다른 작성자의 PENDING·PRIVATE 퀴즈, 정답, 풀이 기록에는 접근할 수 없다. PUBLIC 퀴즈는 정답을 미리 노출하지 않는 공개 풀이 DTO로만 읽는다.
- AC-04f: 1단계는 더미 사용자별 목록·구독 UX를 구분하되 이를 소유권 보안으로 간주하지 않는다. 2단계는 Google 로그인과 내부 User ID로 작성자·구독자를 식별하고 세션·데이터 보존 정책을 적용한다.
- AC-04g: 생성 후보에서 퀴즈 하나를 개별 저장하거나 남은 퀴즈를 각각 일괄 저장할 수 있다. 저장된 각 퀴즈는 독립 ID와 PENDING 상태로 내 목록에 나타난다. 중복 요청으로 같은 후보 퀴즈가 두 번 저장되지 않으며, 일괄 저장은 이미 개별 저장한 퀴즈를 복제하지 않는다.
- AC-04h: 생성 후보별 검토·승인 링크를 반복하지 않는다. 현재 묶음에 남은 모든 후보가 임시저장 또는 바로 공개로 처리된 뒤에만 하나의 검토·승인 진입을 상단에 표시한다. 작성자는 후보를 삭제할 수 있고, 이미 저장·공개한 후보라면 연결된 퀴즈도 soft delete해 목록과 학습 후보에서 숨긴다.
- AC-04i: 생성 모달에 임시저장·공개하지 않은 후보가 남아 있으면 닫기 버튼과 Escape로 닫기 전에 해당 후보가 사라짐을 확인한다. 취소하면 모달과 작업 상태를 유지하고, 남은 후보가 모두 임시저장·공개·삭제된 경우에는 경고 없이 닫는다.

### REQ-05 퀴즈 풀이

작성자는 자신의 PRIVATE 퀴즈를, 로그인한 사용자는 PUBLIC 퀴즈를 풀고 제출 결과를 확인한다. 비로그인 방문자는 AC-05h에 따라 홈에서 PUBLIC 퀴즈를 체험할 수 있다. 채점은 승인된 퀴즈의 정답을 기준으로 서버에서 수행한다. PENDING은 작성자 검토용이며 풀이 기록을 만들지 않는다.

수용 기준:

- AC-05a: PENDING은 작성자 본인도 풀이를 시작할 수 없다. 1단계는 더미 사용자별 PRIVATE/PUBLIC 풀이 UX를 Mock API에서 구분한다. 2단계는 JWT·내부 User ID를 검사해 PRIVATE는 작성자만, PUBLIC은 인증된 사용자 누구나 풀게 한다. 비로그인 홈 체험은 AC-05h의 별도 경로로 허용한다.
- AC-05b: 답을 선택하거나 입력하기 전에는 제출할 수 없다. 제출 전에는 풀이 화면, HTML, 클라이언트 상태 및 풀이 API 응답에 정답·해설·정오 표시를 포함하지 않는다. 작성자가 이전에 본 정답까지 잊게 하는 것은 요구하지 않는다.
- AC-05c: 제출 후 선택 답, 정오, 정답, 해설을 보여준다. 제출 전에는 정답·해설을 반환하지 않는다.
- AC-05d: 같은 풀이의 답을 반복 제출해도 최초 결과와 점수가 유지된다. 다른 답으로 변경 제출하면 거부하고, 정답은 클라이언트가 보내지 않는다. 풀이 시작 시의 승인된 퀴즈 버전으로 끝까지 채점한다.
- AC-05e: 제출 실패 시 선택한 답을 유지하고 재시도를 허용한다. 새로고침 후 같은 풀이의 제출 결과를 복원한다.
- AC-05f: 제출 후 정오와 완료 상태를 보여준다. 다시 풀기는 별도 풀이를 만들어 시작하며 이전 기록을 덮어쓰지 않는다.
- AC-05g: 본문 코드 블록은 풀이 중 표시하고 해설 코드 블록은 해당 퀴즈 제출 후에만 표시한다. 언어·줄바꿈·들여쓰기를 보존하고 실행 버튼이나 코드 실행 채점을 제공하지 않는다. 공개 퀴즈에도 같은 비노출 규칙을 적용한다.

- AC-05h: 비로그인 홈은 전체 활성 PUBLIC 퀴즈에서 무작위 한 문제를 제공한다. 태그 선택·스트릭은 표시하지 않는다. 답 제출 후 정오·정답·해설을 확인하고 다음 랜덤 문제를 풀 수 있다. PRIVATE·PENDING·삭제 퀴즈와 원본 학습 내용은 노출하지 않으며 제출 시 공개·삭제 상태를 재검사한다. 후보가 없으면 빈 상태를 표시한다. 방문자 풀이 기록·학습일·스트릭·BugCoin은 저장·집계·지급하지 않고 로그인 시 이관하지 않는다. 체험은 일시적이며 AC-05d~f의 개인 Attempt 저장·복원 요구는 적용하지 않는다. 익명 OwnerSession은 도입하지 않는다.
- AC-05i: 비로그인 사용자는 탐색·공개 프로필·상품을 둘러볼 수 있다. 구독·구매 클릭과 개인 페이지·작성 기능 진입 시 로그인 안내를 제공한다. 로그인 후 원래 페이지로 복귀하되 구독·구매는 다시 명시적으로 실행한다. 1단계에는 데모 사용자 선택으로 UX만 검증한다.

### REQ-06 버그리 기본 반응

버그리는 추가 AI 호출 없이 미리 정의한 표정·짧은 문구로 학습을 돕는다. 풀이 결과 화면은 정오·해설에 집중하도록 캐릭터와 반응 문구를 표시하지 않는다.

| 상황           | 반응 예시                                   |
| -------------- | ------------------------------------------- |
| 대기           | 기본 표정, “배운 내용을 퀴즈로 바꿔볼까?”   |
| 생성 중        | 기다리는 표정, “문제를 만들고 있어!”        |
| 초안 생성 성공 | 반가운 표정, “정답과 해설을 함께 확인해줘.” |
| 요청 실패      | 기본 표정, “다시 시도해보자.”               |

수용 기준:

- AC-06a: 각 상황에 맞는 반응을 표시한다. 정오 반응은 서버 채점 성공 이후에만 바뀐다.
- AC-06b: 퀴즈 답안 제출 후 정오 반응을 먼저 보여주고 완료 상태에서는 완료 반응을 보여준다.
- AC-06c: 캐릭터 이미지가 로드되지 않거나 애니메이션을 줄이는 설정에서도 텍스트 안내와 핵심 흐름을 사용할 수 있다. 오답에 비난하는 문구를 사용하지 않는다.

### REQ-07 공개 범위 선택과 전환

작성자는 검토를 마친 PENDING 퀴즈를 PRIVATE 또는 PUBLIC으로 승인한다. 승인 후에도 작성자가 PRIVATE↔PUBLIC으로 전환할 수 있다. PRIVATE는 다른 사용자와 오늘의 퀴즈 후보에 노출되지 않는다.

수용 기준:

- AC-07a: 작성자만 자신의 검토 완료 PENDING 퀴즈에 최초 공개 범위를 정하고, 승인된 퀴즈의 공개 범위를 전환할 수 있다. 미검토·미저장 변경·오래된 버전·타인 퀴즈 요청은 거부한다.
- AC-07b: 승인 화면은 대상 퀴즈·해시태그·선택한 공개 범위를 보여주고 명시적 조작을 요구한다. 생성·재생성·검토 완료만으로 자동 승인·공개하지 않는다.
- AC-07c: PUBLIC→PRIVATE 전환 후 공개 목록·구독 기반 학습 대상에서 즉시 제외한다. 타인은 새 풀이를 시작하거나 진행 중 답안을 제출할 수 없으며 이용할 수 없음을 안내한다. 작성자의 PRIVATE 풀이 권한은 유지한다. PRIVATE→PUBLIC 전환 후에는 다시 학습 후보가 될 수 있다.
- AC-07d: PUBLIC 퀴즈는 공개 목록·오늘의 퀴즈에서 문제 풀이에 필요한 정보만 제공한다. 제출 전 정답·해설과 원래 학습 내용은 노출하지 않는다.
- AC-07e: 승인된 퀴즈의 PENDING 수정본을 승인하면 새 버전이 원자적으로 활성화된다. 공개 범위는 작성자가 변경하지 않는 한 유지한다. 기존 풀이 기록은 시작 당시 버전으로 채점·조회한다.

### REQ-08 구독 대상 및 범위

사용자는 다음 세 가지 방식으로 구독할 수 있다.

1. **사용자 구독:** 특정 개발자를 구독하며, 해당 개발자가 공개하는 모든 퀴즈를 학습 대상으로 제공받는다.
2. **해시태그 구독:** 특정 해시태그를 구독하며, 해당 태그가 포함된 모든 개발자의 공개 퀴즈를 학습 대상으로 제공받는다.
3. **사용자별 해시태그 구독:** 특정 개발자의 특정 해시태그를 구독하며, 해당 개발자가 공개한 퀴즈 중 지정한 해시태그가 포함된 퀴즈만 학습 대상으로 제공받는다.

구독 대상은 사용자 또는 해시태그, 혹은 사용자와 해시태그의 조합이다. **퀴즈는 구독 대상이 아니라 구독 조건에 따라 제공되는 학습 콘텐츠이다.** 하나의 퀴즈가 여러 구독 조건에 해당해도 중복 제공하지 않는다. 홈의 학습 퀴즈는 구독 조건과 선택한 태그에 부합하는 PUBLIC 퀴즈에서 선정하며, 조건에 맞는 퀴즈가 없으면 제공하지 않는다.

수용 기준:

- AC-08a: 사용자는 세 가지 조건을 각각 등록·해제하고 현재 구독 조건을 확인할 수 있다. 사람과 해시태그는 공개 퀴즈에 사용되는 안정적인 식별자로 지정한다.
- AC-08b: 오늘의 퀴즈 후보는 사용자가 직접 등록한 구독 조건과 일치하는 PUBLIC 퀴즈뿐이다. 다른 퀴즈의 태그로 일치를 추론하지 않는다. 여러 조건에 일치해도 quizId 기준으로 한 퀴즈로 취급한다.
- AC-08c: PENDING·PRIVATE 퀴즈는 타인의 오늘의 퀴즈 후보나 공개 API에 나타나지 않는다. PUBLIC 전환 후에는 조건에 맞는 구독자에게만 후보가 될 수 있다.

### REQ-09 BugCoin 상점과 데스크

풀이 보상으로 얻은 BugCoin으로 키보드·모니터·책상·소품·배경 카테고리의 아이템을 구매한다. 구매한 아이템은 보관함에 남고 사용자는 내 데스크에 장착·해제할 수 있다. 다른 사용자의 마이페이지는 그 사람이 장착한 데스크를 첫 화면에 보여준다.

수용 기준:

- AC-09a: 풀이 보상 BugCoin의 지급 규칙과 금액을 구현 전에 정한다. 동일한 보상 사유로 중복 지급하지 않으며 XP와 혼동하지 않는다. 사용자는 잔액과 지급·사용 내역을 확인할 수 있다.
- AC-09b: 1단계는 더미 BugCoin 잔액으로 상품 조회→구매→보관함 추가 UX와 잔액 부족·중복 클릭 방지 메시지를 검증한다. 2단계는 재전송·동시 요청에도 한 번만 차감·구매·추가하며 잔액 차감과 보관함 추가를 원자적으로 처리한다.
- AC-09c: 1단계는 더미 보관함에 있는 상품만 장착·해제하는 UX를 제공한다. 2단계는 구매 소유권을 서버에서 확인하고 장착 상태를 MySQL에 보존하며 다른 사용자의 데스크 변경을 막는다.
- AC-09d: 다른 사용자의 마이페이지 첫 화면에서 그 사용자의 장착 데스크가 별도 메뉴 이동 없이 보인다. 장착 아이템이 없어도 기본 데스크를 보여준다. 타인의 BugCoin 잔액·구매 내역·보관함은 공개하지 않는다.
- AC-09e: 데스크와 상품을 실제 3D로 렌더링한다. 내 데스크 편집은 `/my`, 전체 상품 목록·구매와 상품별 장착 미리보기 모달은 `/shop`, 타인 데스크 조회는 `/users/[publicId]`에서 제공한다. 상점에는 이웃의 데스크 섹션/이웃 메뉴와 상점/보관함 전환 탭 없이 전체 상품과 카테고리를 표시하고, 보유 상품 표시와 미리보기 모달의 실제 장착을 제공한다. 보유 상품 관리·해제는 `/my`에서 제공한다. 상점은 상단에 잔액을 표시하고 미보유 상품에만 장착해 보기 버튼을 표시한다. 가격 아래 장착해 보기·구매하기를 가로 배치하며 보유 중 표시는 구매 버튼 위치를 유지한다. 해당 모달에서 현재 공간의 책상·장착 상품·배치를 보존하고 물건을 별도 미리보기 오브젝트로 추가한다. 기존 책상 또는 같은 카테고리 상품이 있으면 옆에 배치한다. 추가 상품과 기존 책상·상품을 각각 선택해 이동/회전할 수 있다. 기존 상품의 변경은 모달 안의 임시 배치이며 실제 장착을 눌러도 저장하지 않는다. 모달을 닫거나 다시 열면 기존 저장 배치로 복원한다. 배경은 환경 미리보기로 전환한다. 정원/달빛 배경은 캔버스 전체의 색감, 입체 방과 가구·버그리 조명에 함께 적용하며 회전 가능한 3차원 구성을 유지한다. 배경은 축소·좌우/상하 회전 시에도 화면 전체를 방 내부로 채우며 유한한 벽·바닥의 외곽이나 배경 밖 빈 영역을 드러내지 않는다. 창문·러그와 벽/바닥 경계의 입체감은 유지한다. 서로 만나는 벽의 모서리는 수직선으로 유지하며 벽 겹침으로 사선 경계가 생기지 않는다. 상품 썸네일에서도 벽 하단과 바닥 모서리를 맞춰 벽이 바닥 범위를 초과하지 않게 한다. 버그리는 구매할 필요 없는 기본 캐릭터이며 클릭/드래그·회전·높이 조절이 가능하다. 내 공간의 버그리 배치는 사용자별 저장·공개 복원하고 미리보기의 변경은 임시로만 유지한다. 실제 저장은 현재 카테고리당 하나의 장착 계약을 유지하므로 기존 상품이 있는 경우 교체 버튼으로 구분한다. 미리보기만으로 잔액·보관함·실제 장착을 변경하지 않으며 구매/실제 장착은 별도 명시적 버튼으로 처리한다. 상점 모달의 화면 너비는 내 데스크와 같고 상품을 클릭하면 선택 테두리와 위쪽 모서리에서 작게 돌출된 회전 화살표가 나타난다. 상하 화살표 핸들은 표시하지 않는다. 선택 테두리 옆 … 메뉴에서 앞으로 가져오기/뒤로 보내기는 한 단계, 맨 앞으로/맨 뒤로 보내기는 끝 순서로 이동한다. 순서는 높이·좌표와 별개이며 선택만으로 바꾸지 않는다. 내 공간은 순서를 저장하고 공개 공간에서 동일하게 표시한다. 미리보기에서는 기존 아이템 순서 변경을 임시로만 유지하고 실제 장착 시 추가 상품의 순서만 반영한다. 완전히 가려진 아이템도 키보드 선택 시 테두리/메뉴로 다시 앞으로 가져올 수 있다. 내 데스크와 미리보기는 상단 도구 버튼 없이 상품을 직접 드래그해 이동하고 빈 공간을 좌우·상하로 드래그해 시점을 회전한다. 좌우·상하 모두 공간을 잡아 끄는 방향을 따라 회전한다. 위로 끌면 가까운 쪽이 올라가며 책상 아랫면을, 아래로 끌면 가까운 쪽이 내려가며 윗면을 볼 수 있다. 상하 시점은 -85~85도로 책상 위와 아래까지 둘러볼 수 있다. 장착해보기 공간 영역의 마우스 휠·트랙패드로 0.5~2.5배 확대/축소할 수 있고 배치 좌표는 바뀌지 않는다. 아이템 조작 후 회전 버튼·선택 메뉴 위에서도 동일하게 확대/축소한다. 공간 영역 밖에서는 기존 페이지 스크롤을 유지한다. 장착해보기에는 상품별 선택 버튼 없이 초기화 버튼만 표시하며, 초기화 시 기존 상품과 추가 상품의 임시 배치 및 시점·확대 비율을 처음 상태로 되돌린다. 키보드 사용자는 미리보기 캔버스에서 Home으로 첫 상품, PageDown/PageUp으로 다음/이전 상품을 선택하고 방향키(Alt: 회전, Shift+↑↓: 높이)로 조절한다. 내 데스크의 상품 선택 버튼은 유지한다. 상품 이동·회전·높이와 시점 회전을 분리하며 임시 배치를 편집할 수 있다. 실제 장착 버튼은 추가 대상 상품만 장착 후 해당 임시 배치를 저장한다. 장착 후 배치 저장만 실패하면 그 상태를 알리고 초안을 유지해 재시도한다. 상점 모달에서는 빈 공간 드래그로 시점을 회전하고 정면·45도·위쪽 시점 버튼은 표시하지 않는다. 내 데스크와 공개 공간은 기존 시점 선택을 유지한다. 상품 이동과 회전은 카메라 조작과 분리한다. 장착한 키보드·모니터·소품은 책상 안팎에서 자유롭게 이동하고 수직축 회전 핸들로 방향을 바꾼다. 선택 테두리 위의 작은 회전 화살표을 누른 채 좌우로 드래그하면 각도가 연속 반영되고 놓으면 확정한다. 포인터 단순 클릭으로는 회전하지 않는다. 키보드 방향키 조절은 유지한다. 상판 외곽 제한 없이 이동·회전할 수 있다. 키보드·모니터·소품·버그리를 움직일 때 잡은 지점과 모델 바닥 접점의 화면상 간격을 유지하며 접점이 현재 책상 상판에 닿으면 드래그 중부터 실제 3D 위치와 높이를 상판에 맞추고, 드롭·시점 회전 후에도 유지한다. 기존 아이템과 추가 미리보기 아이템에 동일하게 적용하며 받침 크기와 책상 대비 회전각을 반영해 상판 가장자리에서도 받침이 지지되도록 한다. 포인터를 직접 상판에 놓는 드롭도 지원한다. 상판 윗면을 볼 수 없는 정면/아래쪽 시점에서는 자동 상판 맞춤을 하지 않는다. 상판 밖 드롭은 기존 자유 배치와 높이를 유지하며 취소·단순 클릭·회전은 자동 높이 맞춤을 하지 않는다. 정면 부근(카메라 높낮이 -20~20도)에서 책상을 제외한 아이템의 세로 드래그는 카메라 기준 깊이를 유지하며 높이를 바꾼다. 이 구간에서는 상판 스냅을 하지 않고 가로 드래그는 화면 좌우로 이동한다. 기본 비스듬한 시점을 포함한 -45~45도에서는 세로 방향으로 시작한 드래그도 같은 높이 조절로 처리한다. 드래그 도중 이동 평면은 바꾸지 않으며 아래로 내릴 때 상판에 다시 붙이지 않는다. 바닥에서 위로 올려 상판에 놓는 드롭은 유지한다. 이 동작은 버그리·키보드·모니터·소품의 기존/추가 아이템에 동일하게 적용한다. 그 외 수평 이동은 현재 높이를 유지하고, Shift+위아래 방향키·슬라이더·숫자 입력으로 높이를 조절한다. 바닥(0)/상판(1.55) 프리셋을 제공한다. 상품 높이는 0 이상이며 책상 자체는 바닥에 유지한다. 겹침 순서를 따로 지정하지 않은 경우 상판 아래 상품은 상판에 가려지고 시점에 따라 다리 사이로 보인다. 드래그 중과 드롭·높이 변경·저장 재조회 후에도 현재 확대 비율과 화면 중심 기준을 유지한다. 공간의 좌우 회전은 책상·버그리·상품을 포함한 전체 배치가 화면 중앙에 오도록 구도를 보정한다. 버그리 하나나 고정 책상 원점만을 중심으로 삼지 않는다. 최소 배율에서도 방 배경과 전체 배치가 같은 중심을 사용해 회전 시 방 안에서 좌우로 쏠리지 않게 한다. 방 안에서 바라보는 원근 구도로 정면 근처에도 양쪽 벽과 바닥이 함께 보이게 한다. 방과 가구는 같은 시점으로 회전하며 방 배경만 역회전해 고정하지 않는다. 휠 확대/축소 시 벽·창문과 아이템에 같은 배율을 적용하며 배경 크기만 고정하지 않는다. 방은 직각으로 만나는 사각형 구조이며 축소할 때 카메라 쪽 벽이 추가로 꺾여 들어온 다각형처럼 보이지 않게 한다. 공간 최초 열기·상품 구성 변경·초기화에서만 전체 배치에 맞춰 기준 범위를 계산하며, 배치 변경만으로 자동 축소하지 않는다. 장착해보기에서는 책상만 바닥에서 독립 이동·회전하며 기존 소품·추가 상품·버그리는 모달을 열었을 때의 좌표 기준을 유지한다. 내 데스크의 책상 이동·회전은 기존대로 위 상품과 함께 움직인다. 배경은 고정한다. 키보드 조절도 제공한다. 내 데스크와 장착 미리보기에는 아이템 회전 슬라이더, 좌표·각도 수치와 상시 조작 안내 문구를 표시하지 않는다. 키보드 사용자의 배치 피드백은 스크린리더 전용 상태로 제공한다. 위치·높이·회전은 사용자별로 저장·복원하고 타인 데스크에서도 동일하게 표시한다. 저장 실패 시 초안을 유지하고 재시도·취소를 제공한다.

### REQ-10 관리자 상품 등록

관리자는 상품명·설명·카테고리·BugCoin 가격을 직접 입력해 신규 상품을 등록한다. 상품 등록에 AI 생성이나 주기 스케줄러를 사용하지 않는다.

수용 기준:

- AC-10a: 2단계에서는 Google OAuth2·JWT와 내부 User 권한을 확인한 관리자만 상품 등록 API에 접근할 수 있다. 1단계 상점 UX에는 실제 관리자 인증을 요구하지 않는다.
- AC-10b: 상품명·설명·허용 카테고리·양수 BugCoin 가격을 서버에서 검증한다. 누락·잘못된 가격·중복 상품은 판매 목록에 올리지 않는다.
- AC-10c: 등록 요청을 재전송해도 상품이 중복 생성되지 않는다. 실패 시 기존 판매 상품과 구매 내역은 유지한다.
- AC-10d: 등록된 상품은 상점에서 카테고리별로 조회·구매할 수 있다. 1단계 상품 시각 자산은 직접 제작한 3D 모델을 상품 ID별로 연결한다. 상품 카드의 렌더 이미지와 데스크에서 같은 모델을 사용한다. 상품 카드·내 데스크·공개 데스크는 WebGL을 요청하지 않는 Canvas 기반 입체 렌더러를 사용한다. 카드 이미지 생성 실패 시 기존 일러스트를 유지한다. 깊이 정렬에 따른 복잡한 교차 면 표현의 한계가 있다. 2단계 관리자 자산 업로드·입력 방식은 별도로 정한다.

### REQ-11 퀴즈 수정·재생성·삭제

작성자는 PRIVATE·PUBLIC 퀴즈도 직접 수정하거나 추가 프롬프트로 LLM에 다시 생성하도록 요청할 수 있고, 자신의 퀴즈를 삭제할 수 있다. 내용 변경은 기존 풀이를 훼손하지 않는 새 수정본으로 처리한다.

수용 기준:

- AC-11a: 작성자는 승인된 퀴즈에서 원래 학습 내용·퀴즈를 직접 수정하거나 LLM 재생성을 시작할 수 있다. 새 결과는 PENDING 수정본이며 기존 승인 버전은 그대로 서비스된다. 타인은 수정본에 접근할 수 없다.
- AC-11b: 수정본을 다시 검토·승인하면 새 버전이 활성화된다. 제출 권한이 유지되는 풀이는 시작 당시 버전의 문제·정답·해설로 채점한다. 이미 완료한 점수와 제출 결과는 바뀌지 않는다. 아직 선정되지 않은 오늘의 퀴즈 후보는 새 활성 버전의 문제·해시태그를 기준으로 판단한다.
- AC-11c: 작성자만 자신의 PENDING·PRIVATE·PUBLIC 퀴즈를 삭제할 수 있다. 삭제 즉시 사용자 화면과 구독 기반 학습 대상에서 숨기고 새 풀이·수정·재생성·진행 중 답안 제출을 차단한다. 이용할 수 없음을 안내하며 중복 삭제 요청은 안전하게 처리한다.
- AC-11d: 서버는 삭제된 퀴즈를 삭제 상태로 관리한다(soft delete). 비공개 전환·삭제 전 완료한 풀이 기록과 학습 성과(스트릭·XP·BugCoin)는 유지하며 취소·차감·재계산으로 소급 제거하지 않는다. 기록 보존이 삭제된 문제 본문의 재노출을 뜻하지 않는다. XP 보존 정책은 XP 기능의 1단계 추가를 요구하지 않는다.

### REQ-12 홈의 학습 태그와 연속 풀이

로그인 사용자는 홈 학습 영역에서 기술 해시태그를 선택하고 조건에 맞는 퀴즈를 한 문제씩 이어 푼다. 구독 피드와 무한 스크롤은 제공하지 않는다. 기존 하루 최대 1개 제한과 당일 문제 고정은 적용하지 않는다.

수용 기준:

- AC-12a: 기본 선택은 '전체'다. 별도 선택이 없으면 모든 직접 구독 조건에 해당하는 PUBLIC 퀴즈를 학습 후보로 사용한다. MVP에서는 한 번에 한 해시태그만 선택한다.
- AC-12b: 선택지는 구독 조건에 해당하는 PUBLIC 퀴즈의 해시태그로 제공한다. 구독한 개발자를 기준으로 태그를 조회할 때도 같은 공개·구독 범위를 적용한다. 태그 선택은 구독 상태를 변경하거나 구독 밖 퀴즈를 후보로 추가하지 않는다.
- AC-12c: 태그를 선택하면 직접 구독 조건과 해당 태그를 모두 만족하는 PUBLIC 퀴즈만 출제한다. 여러 구독 조건에 맞아도 quizId로 중복 제공하지 않는다.
- AC-12d: '다음 문제'에서도 현재 태그를 유지하고 해당 범위의 미풀이 퀴즈를 제공한다. 미풀이는 사용자의 완료 기록이 없는 quizId를 기준으로 판단한다. 다른 태그에서 완료한 같은 퀴즈를 새 미풀이로 취급하지 않는다.
- AC-12e: 마지막 문제의 결과 화면까지는 '다음 문제'를 유지한다. 이를 누른 뒤 해당 태그의 미풀이 퀴즈가 없으면 소진 제목·안내와 '태그 탐색'을 제공하고 완료 문제를 다시 선택하지 않는다. 다른 quizId로 저장됐더라도 문제 형식·본문·선택지가 같은 완료 문제는 미풀이 후보에서 제외한다. 개별 결과의 '다시 풀기'는 해당 퀴즈에 새 Attempt를 만들며 기존 기록을 덮어쓰지 않는다. 후보 자체가 없을 때도 태그 탐색과 구독을 안내한다.
- AC-12f: 태그를 변경해도 기존 풀이 기록과 완료 기록을 유지한다. 태그 변경은 필터 변경이며 구독 추가·해제를 호출하지 않는다.
- AC-12g: 선택 태그·정답 여부에 관계없이 사용자 학습 시간대의 하루에 퀴즈 1개 이상을 완료하면 학습일로 인정한다. 신규 문제와 다시 풀기 모두 인정하며 같은 날짜에 여러 문제를 풀어도 한 번만 집계한다. 태그 변경은 당일 충족 상태를 초기화하지 않는다.
- AC-12h: 제출 전 정답·해설을 홈 HTML·클라이언트 상태·풀이 API 응답에 넣지 않는다. 완료 후 완료 상태와 버그리 반응을 표시하며 개인 퀴즈 목록·풀이도 유지한다.
- AC-12i: 학습할 문제가 없는 상태에서 ‘태그 탐색’을 누르면 전용 탐색 페이지로 이동하고 프로젝트의 모든 개발자와 등록 태그를 검색할 수 있다. 개발자·태그를 구분해 검색하며 결과는 API에서 페이지 단위로 조회한다. 검색어·검색 대상·페이지는 URL로 복원한다. 검색은 구독 범위 밖과 아직 공개 퀴즈가 없는 태그도 포함한다. 검색 자체는 구독을 변경하지 않으며 구독 등록은 명시적인 조작으로 수행한다. 구독 추가 후 탐색 페이지와 검색 조건을 유지해 여러 항목을 연속 추가할 수 있어야 하며, 학습 이동은 별도 명시적인 조작으로 수행한다.
- AC-12j: 탐색 결과의 개발자 이름을 클릭하면 해당 개발자의 개인 공개 퀴즈 페이지로 이동한다. 해당 개발자의 PUBLIC 퀴즈와 사용 태그를 페이지 단위로 조회하고 태그로 퀴즈를 필터링한다. 퀴즈 선택은 기존 풀이로 연결한다. 개발자 전체 또는 해당 개발자의 특정 태그를 명시적으로 구독하며 등록 후 페이지에 머문다. 비공개·검토 중·삭제된 퀴즈와 제출 전 정답·해설·원문은 공개 목록에 포함하지 않는다.

### 스트릭 시간대 정책

- 최초 접속 시 브라우저의 IANA 시간대(예: Asia/Seoul, America/New_York)를 감지한다. 감지할 수 없으면 Vercel의 IP 기반 시간대를 사용할 수 있는지 검토한다. IP 국가 코드만으로 시간대를 정하지 않는다.
- 시간대를 확인할 수 없으면 명시적인 기본 시간대를 적용하고 변경 방법을 안내한다. 기본 시간대 값은 아직 미결정이다. 사용자는 마이페이지에서 자신의 학습 시간대를 확인·변경할 수 있으며 저장한 설정을 이후 접속에도 사용한다.
- 시간대 변경으로 완료 기록·이미 지급한 보상을 소급 변경하지 않는다. 1단계는 Mock 데이터와 브라우저 상태로 검증한다. 2단계는 서버가 완료 시각을 UTC로 기록하고 사용자별 시간대를 적용해 학습일을 계산한다.
- 2단계는 시간대 변경을 이용한 일일 보상 중복 수령을 방지한다. 브라우저 시간대를 그대로 신뢰하는 방식은 실제 보상의 보안 기준이 아니다. 변경 전후 일일 보상 중복 판정의 세부 기준은 백엔드 구현 전에 결정한다.

### REQ-13 2단계 Google 로그인·JWT·내부 User ID

2단계 사용자는 Google OAuth2로 로그인하고 JWT로 API 인증을 받는다. 서버는 검증된 Google 계정을 내부 User에 연결하고 내부 User ID로 소유권과 권한을 판단한다. 1단계는 실제 인증을 구현하지 않으며 더미 사용자를 화면 검증에만 쓴다. 익명 OwnerSession은 사용하지 않는다.

수용 기준:

- AC-13a: 2단계 REST API는 Google OAuth2 로그인 시작·콜백·현재 사용자 조회·로그아웃과 JWT 검증을 제공한다. 인증 실패·취소를 처리하고 인증 없는 작성·구독·개인 기록을 남기는 풀이·구매 요청을 거부한다. AC-05h의 비로그인 홈 체험은 별도로 허용한다. 1단계 더미 사용자 전환은 로그인으로 표시하지 않는다.
- AC-13b: 검증한 Google 계정의 불변 식별자와 내부 User ID를 유일하게 연결한다. 이메일·표시 이름 변경이 소유권을 바꾸지 않는다. 같은 Google 계정의 재로그인은 기존 User를 사용한다.
- AC-13c: 2단계에서 퀴즈·구독·풀이·BugCoin·구매·보관함·데스크의 소유권은 검증된 JWT와 내부 User ID로 판단한다. 요청에 포함된 임의 userId·ownerId를 신뢰하지 않는다.
- AC-13d: 2단계 관리자 권한은 내부 User에 부여·검증한다. Google 로그인만으로 관리자 권한이 생기지 않는다.

## 6. 품질과 단계별 완료 기준

- UI 스타일링은 Tailwind CSS v4와 공통 디자인 토큰을 사용한다. CSS-in-JS는 도입하지 않으며, 공통 컴포넌트의 상태·반응형·키보드 접근성을 일관되게 유지한다.

- 모든 단계에서 화면은 모바일·데스크톱과 키보드로 핵심 동작을 수행할 수 있어야 한다. 코드 블록을 실행하지 않고, 미제출 정답·해설을 풀이 화면과 API 응답에 노출하지 않는다.
- 1단계는 API 요청·응답 타입을 정의하고 Mock API로 퀴즈 생성·개별/일괄 저장·풀이, 3종 구독, 태그별 연속 풀이와 하루 1개 완료 조건, BugCoin 구매·장착 UX를 구현한다. Mock 파일 초기 데이터와 더미 사용자별 localStorage 변경 상태로 프로토타입 상태를 유지한다. Jest·React Testing Library·Playwright로 검증하고 Vercel에 배포한다. DB 연결·MySQL/Prisma/mysql2 설치·실제 JWT/OAuth·실제 AI·실제 구매 트랜잭션은 1단계 완료 조건이 아니다.
- 1단계의 더미 사용자·Mock 인증은 보안 기능이 아니다. 더미 데이터와 사용자 전환 UI가 있으면 프로토타입임을 알린다. Mock 정답 비노출·권한 제어도 UX 검증이며 실제 보안 보장이 아니다. localStorage는 사용자별 영구 저장소가 아니며 브라우저 데이터 삭제·기기 변경 시 유실될 수 있음을 안내한다.
- 2단계는 Spring Boot·Java 21·MySQL 8.4·Spring Data JPA로 Mock API를 실제 REST API로 교체한다. Google OAuth2·JWT와 내부 User ID로 소유권을 검증하고, 퀴즈·구독·풀이·BugCoin을 영속화한다. 구매·포인트 차감·보관함 추가를 트랜잭션으로 처리하며 중복·동시 요청을 검증한다.
- 전체 제품의 상점 요구사항과 관리자 직접 상품 등록 정책은 유지한다. 1단계에 실제 관리자 보안·상품 등록 백엔드를 추가하지 않는다. 구독 피드·PG·현금 결제는 1단계 범위에서 제외한다.

## 7. 확정 정책과 미결정 사항

확정: 1단계 Next.js 16·TypeScript, DB 없는 더미 데이터·Mock API, 더미 사용자, 사용자별 localStorage 변경 상태, Jest·React Testing Library·Playwright, Vercel 프로토타입 배포. 2단계 Spring Boot·Java 21, MySQL 8.4·Spring Data JPA, JWT·Google OAuth2, 실제 영속성·구매 트랜잭션·동시성 처리. API 요청·응답 타입은 1단계부터 유지한다. 요청당 독립 퀴즈 1~5개·개별/일괄 저장·퀴즈당 해시태그 최대 3개, 3종 직접 구독과 태그별 연속 풀이와 하루 1개 완료 조건, BugCoin 상점은 제품 정책이다. Kubernetes는 별도 실습 환경이다.

미결정: 퀴즈 문제 형식, 실제 AI 제공자·모델과 2단계 연동 시점, 시간대 미감지 시 사용할 명시적 기본 시간대와 Vercel IP 시간대 제공 가능 여부, JWT 만료·갱신·폐기 정책, Google OAuth2 구현 세부 방식, 일반 데이터 보존 기간(퀴즈 삭제 방식과 완료 성과 유지 정책은 확정), BugCoin 지급량, 2단계 관리자 상품 시각 자산 입력 방식, 2단계 Spring Boot 배포 환경과 MySQL 호스팅·연결 방식. 1단계에 DB·실제 인증을 도입할지는 미결정 사항이 아니라 이번 단계의 제외 정책이다.
