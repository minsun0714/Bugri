# Bugri 아키텍처

## 1. 단계와 책임

[PRD.md](PRD.md)의 전체 제품 요구사항을 유지하면서 개발을 두 단계로 나눈다. 현재 작업 대상은 **1단계 Next.js 프로토타입**이다.

| 단계  | 기술                             | API·데이터                                                                       | 인증·배포                                                                                               |
| ----- | -------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 1단계 | Next.js 16 App Router·TypeScript | 타입 기반 Mock API 어댑터, 파일 초기 데이터·localStorage 변경 상태. DB 연결 없음 | 화면 검증용 더미 사용자. 실제 JWT·OAuth 없음. Jest·React Testing Library·Playwright 검증 후 Vercel 배포 |
| 2단계 | Spring Boot·Java 21              | MySQL 8.4·Spring Data JPA, 실제 REST `/api/v1`                                   | Google OAuth2 로그인·JWT 인증·내부 User ID 소유권. 실제 영속성·구매 트랜잭션·동시성 처리                |

1단계에는 MySQL·Prisma·mysql2를 설치하거나 연결하지 않는다. 2단계의 DB·인증·동시성 설계는 향후 구현 계약이며 현재 프로토타입의 보안·영속성 보장을 뜻하지 않는다. Kubernetes는 별도 실습 환경이다. 2단계 Spring Boot의 배포 환경은 아직 정하지 않았다.

```text
1단계: UI → 타입이 정의된 API 클라이언트 → 브라우저 Mock 어댑터 → Mock 파일 초기 데이터 + 사용자별 localStorage 변경 상태
2단계: 같은 UI/API 클라이언트 → Spring Boot REST /api/v1 → 서비스 → Spring Data JPA → MySQL 8.4
                                           ↘ Google OAuth2·JWT 인증
```

UI 컴포넌트가 더미 배열을 직접 import하거나 더미 사용자 ID를 소유권의 진실로 삼지 않는다. 요청·응답 타입과 오류 형식은 1단계부터 정의하고 Mock API가 그 계약을 따른다. 2단계에는 API 클라이언트의 엔드포인트 구현을 교체한다. Next.js Route Handler와 Spring Controller는 HTTP 변환만 담당하며 퀴즈 선정·채점·구매 규칙은 서비스 계층에 둔다. Next.js 코드를 구현할 때는 설치된 `node_modules/next/dist/docs/`의 관련 가이드를 먼저 읽는다.

### UI와 상태의 책임

제품 API에 연결되는 화면은 `UI → 필요할 때 기능 흐름 훅 → TanStack Query 조회·변경 훅 → 타입 API 클라이언트 → Mock 어댑터/향후 Spring Boot` 경계를 사용한다. 첫 API 연동 화면에서 QueryClientProvider와 의존성을 추가한다. 현재 공통 UI 전시는 API를 호출하지 않으며 단순 로컬 상태를 Query 캐시에 넣지 않는다.

채점·보상·구매 등 제품 규칙은 API 뒤 서비스가 결정한다. React 밖에서 사용할 수 있는 순수 입력 검증·텍스트 변환과, 상태·이벤트·비동기 흐름을 조율하는 훅을 구분한다. 작은 토글·표시용 계산은 컴포넌트에 두어도 된다. 사용자별 캐시 격리, mutation 이후 관련 데이터 갱신, 입력 보존·초기화 등 구체적인 구현 기준은 [implement-feature](../.agents/skills/implement-feature/SKILL.md#ui비즈니스-규칙api-상태-분리)를 따른다.

### 퀴즈 작성 화면

`/quizzes/authoring`은 바깥 학습 입력과 생성 버튼을 제공한다. 퀴즈 선택은 공통 Tabs의 키보드 탐색을 사용한다. 후보 카드에는 퀴즈와 직접 수정·LLM으로 수정 버튼을 표시한다. 직접 수정은 후보 카드 아래에 펼치고, LLM 수정은 Modal 본문 전체를 별도의 대화 화면으로 전환한다. 대화 화면에서 퀴즈로 돌아가도 후보별 로컬 초안과 미전송 요청을 보존하고 반영·취소는 해당 후보에만 적용한다. 미반영 초안이 포함된 일괄 저장은 막고 페이지 이탈 경고를 유지한다. 저장은 해당 콘텐츠 하단에 표시한다. 생성 후 공통 Modal에는 후보를 먼저 표시한다. 내장된 생성 결과는 Modal과 작업 공간의 overflow를 잠그고 공통 Tabs의 panel에만 세로 스크롤을 둬 헤더와 퀴즈 선택 탭을 고정한다. 바로 공개는 후보 한 개의 명시적 검토·PUBLIC 승인 요청이며 서비스의 publishCandidate에서 검증·저장을 한 번에 수행한다. batch 쿼리 파라미터로 반영된 작업을 새로고침 후 복원한다. 기존 `/quizzes/authoring/results?batch={id}` 직접 접근은 유지하되 생성 후 자동 이동하지 않는다. `/quizzes/authoring/manage`는 저장한 퀴즈의 검토·승인·관리를 담당한다. 검토 상세는 저장된 미리보기를 기본으로 표시하고 직접 수정할 때만 편집 폼으로 전환한다. 추가 프롬프트 재생성은 직접 수정과 나란한 버튼에서 공통 Modal을 열고, 실패하면 입력과 모달을 유지하며 성공하면 닫고 새 PENDING 미리보기로 돌아간다. 수정 저장 후 미리보기로 돌아가며, 화면의 승인 한 번이 `MARK_REVIEWED`와 `approve`를 최신 버전으로 순서대로 요청한다. 승인된 기존 버전은 PENDING 수정본이 있을 때 접힌 비교 영역으로만 제공한다. 후보의 직접 편집·추가 요청은 타입 API에서 검증하고 새 candidateId로 오래된 수정 충돌을 막는다. UI는 Mock·localStorage를 직접 접근하지 않는다. 미반영 편집·추가 요청은 모달 닫기 시 유지하며 페이지 이탈 경고를 적용한다.

Modal 자체는 `overflow-hidden`을 유지한다. 작성 작업 본문도 외부 스크롤을 만들지 않으며, LLM 대화 화면의 메시지 컨테이너와 일반 후보 화면의 후보 컨테이너가 각각 내부 스크롤을 담당한다.

LLM 대화 본문의 ref는 대화 mode 진입과 candidateId 변경을 감지해 `scrollTop`을 `scrollHeight`로 맞춘다. 화면을 다시 열거나 재생성 응답으로 후보가 교체될 때 최신 메시지를 표시한다.

직접 수정 mode에서는 `ContentPreview`를 렌더링하지 않고 후보별 `ContentFields`만 렌더링한다. 초안 반영·취소와 mode 전환 상태는 기존 `useGeneration` 경계를 유지한다.

`useGeneration`은 후보별 직접 수정 초안과 LLM 요청 초안을 별도 map으로 유지한다. 직접 수정 초안이 있어도 `refineCandidate`를 호출할 수 있고, 성공한 LLM 결과 뒤에도 직접 수정 초안을 보존한다. 이후 `editCandidate`를 반영하면 최신 candidateId를 사용해 그 내용을 현재 후보로 교체하므로 마지막으로 성공한 반영 결과가 유효하다.

관리 상세는 목록 복귀·제목·상태를 하나의 sticky 헤더로 묶는다. `ContentFields`는 기본 정보·문제 구성·해설·분류 섹션을 제공하고, 원본은 접힌 상태로 두며, 추천 태그는 입력 아래의 칩으로 표시한다. 편집 중 변경 상태·취소·저장은 viewport 하단 고정 바가 담당하고, 재조회는 보조 아이콘, 삭제는 비편집 상태의 독립 위험 영역으로 분리한다.

생성 후보별 검토·승인 링크는 두지 않는다. 남은 후보가 모두 저장 또는 공개되면 첫 번째 처리된 퀴즈로 이동하는 단일 검토·승인 진입을 상단에 표시한다. 후보 삭제는 타입 API로 묶음을 갱신하며, 이미 저장·공개된 후보의 연결 퀴즈는 기존 `deletedAt` soft delete 규칙을 적용한다. 모든 후보를 삭제한 `GenerationBatch`는 빈 배열을 정상 상태로 저장·복원한다. 생성 모달은 미처리 후보가 남은 경우에만 닫기를 확인하며, 공통 Modal은 cancel 이벤트의 기본 닫기를 막고 주입된 `onClose`가 승인한 상태 변경으로만 닫힘을 제어한다. UI는 Mock나 localStorage를 직접 변경하지 않는다.

### UI 스타일링

Tailwind CSS v4를 `@tailwindcss/postcss`로 Next.js 빌드에 연결한다. `src/app/globals.css`의 `@theme`에서 색상·폰트·애니메이션 토큰을 정의하고, 컴포넌트는 Tailwind 유틸리티로 레이아웃·상태·반응형을 표현한다. 긴 클래스 조합은 해당 디렉터리의 `styles.ts`에 완성된 문자열로 둔다. 이는 빌드 시 추출되는 클래스 목록이며 CSS-in-JS 런타임이 아니다.

Markdown과 구문 강조처럼 라이브러리가 생성하는 자식 요소는 컨테이너의 arbitrary variant로 범위를 제한한다. 캐릭터 도형·가상 요소 역시 Tailwind로 표현한다. 전역 CSS는 import·테마·keyframes·문서 기본/접근성 규칙에 한정하며, 별도 컴포넌트 CSS·CSS Modules·twin.macro는 사용하지 않는다. 색상 견본도 공통 토큰을 사용한다.

## 2. 1단계 Mock API와 상태

- Mock API는 독립 퀴즈 1~5개 생성 응답, 개별·일괄 PENDING 저장, 검토·공개 범위·풀이, 3종 구독, 학습 태그·다음 문제·다시 풀기·하루 1개 완료 조건, BugCoin 상품 조회·구매·보관함·장착 UX를 지원한다. AI 제공자 호출 대신 고정·가변 더미 응답으로 성공·실패를 재현한다.
- 더미 사용자 전환은 화면 검증용이다. 누구나 요청을 조작할 수 있으므로 Mock 인증·권한 검사는 실제 보안 기능이 아니다. 실제 개인 정보·비밀값·결제 정보는 더미 데이터에 넣지 않는다.
- 초기 데이터는 `src/mocks/users.ts`, `quizzes.ts`, `subscriptions.ts`, `shop-items.ts`, `learning-history.ts` 등의 프로젝트 파일에서 읽는다(경로 예시이며 이번 작업에서 생성하지 않는다). 최초 사용자는 초기 데이터로 시작하고 저장된 사용자 변경 상태가 있으면 복원한다. 퀴즈 생성·수정·soft delete, 구독·해제, 풀이 기록·BugCoin 구매·장착·시간대 설정은 더미 userId로 구분한 localStorage에 저장한다.
- UI는 Mock 파일·localStorage를 직접 접근하지 않고 타입이 정의된 API 클라이언트와 Mock 어댑터를 이용한다. localStorage 어댑터는 HTTP Route Handler 호출 없이 같은 요청·응답 계약으로 동작할 수 있다. 서버 메모리는 영속 저장소로 쓰지 않는다.
- 로컬 개발에서는 초기 Mock 파일을 수정할 수 있다. 배포 환경에서는 읽기 전용 초기 데이터로 취급하며 Vercel 서버 파일 시스템에 사용자 데이터를 쓰지 않는다. 개발자 탐색 요약은 다른 사용자 스냅샷의 손상만 격리하여 해당 요약을 조회 불가로 표시한다. 현재 사용자 손상은 오류로 유지하며 자동 초기화하지 않는다. 구독 조회·변경은 현재 사용자 상태만 읽고 공개 사용자·태그 디렉터리는 스냅샷을 읽지 않는다. localStorage는 사용자별 영구 저장소가 아니므로 브라우저 데이터 삭제·기기 변경 시 유실될 수 있음을 안내한다.
- Vercel 배포에는 DB 접속 정보·Google OAuth 자격 증명·JWT 비밀키가 필요하지 않다. 배포는 화면·Mock API 동작을 확인하는 프로토타입 배포다. 서버리스 인스턴스 메모리를 운영 저장소로 취급하지 않는다.
- Jest는 도메인 규칙·API 계약과 React Testing Library UI 동작에 사용하고 Playwright는 사용자 여정 E2E에 사용한다. 풀이용 Mock API 응답에도 미제출 정답·해설을 넣지 않고, 사용자 코드를 실행하지 않는다. Mock 파일·브라우저 저장소의 데이터는 사용자가 확인·수정할 수 있으므로 정답 비노출·권한 제어는 UX 검증이며 실제 보안 보장이 아니다.

## 3. 공통 제품 모델과 2단계 영속화

1단계의 타입과 2단계의 영속 엔티티는 같은 개념을 표현한다. 아래의 2단계 필드·제약은 향후 실제 구현 대상이다.

| 개념                                | 공통 계약 및 2단계 규칙                                                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| User                                | 내부 `userId`, Google `sub`(유일), publicId, displayName, role, learningTimeZone(IANA). 이메일은 소유권 키가 아니다. 1단계에는 더미 사용자만 둔다 |
| Quiz                                | 후보 하나당 독립 quizId, ownerUserId, PENDING/PRIVATE/PUBLIC, 활성·검토 중 revision, deletedAt(soft delete)                                       |
| QuizRevision                        | 한 문제·정답·해설·원본 학습 내용·코드 블록·reviewed·최대 3개 해시태그. 승인 버전은 불변                                                           |
| GenerationBatch                     | 요청당 후보 퀴즈 1~5개와 저장 여부. 개별 저장은 후보 1개, 일괄 저장은 남은 후보 각각에 독립 quizId 부여                                           |
| Subscription                        | subscriberUserId, PERSON / PERSON_HASHTAG / HASHTAG, authorUserId?, hashtagId?                                                                    |
| LearningSelection                   | userId, hashtagId?(null은 전체), 현재 quizId·revisionId. 다음 문제에서도 태그 유지                                                                |
| LearningDay                         | userId·사용자 시간대 기준 학습일, 판정에 사용한 시간대. 완료된 날짜는 소급 변경하지 않고 같은 날짜 중복 집계 방지                                 |
| Attempt                             | solverUserId·quizId·revisionId·제출 결과·completedAt(2단계 서버 UTC 시각). 시작한 버전으로 채점하며 미제출 정답은 비공개                          |
| Product / Inventory / DeskEquipment | 관리자 등록 상품, 구매한 상품 보관함, 장착 상태·기준 좌표계의 상품별 이동량                                                                       |
| BugCoinLedger / Purchase            | 보상·차감 원장, 구매 요청 키. 2단계에서 잔액·중복 요청·동시성 제어                                                                                |

구독 대상은 사용자·해시태그·사용자와 해시태그의 조합이며, 퀴즈는 조건에 따라 제공되는 학습 콘텐츠다. Subscription은 quizId를 구독 대상으로 받지 않는다.

퀴즈 생성 묶음은 공개·구독·풀이 단위가 아니다. 독립 퀴즈별로 해시태그 최대 3개, 상태, 수정·삭제, 풀이 기록을 가진다. 승인된 퀴즈 수정·재생성은 새 PENDING revision에서 처리하고 이전 풀이의 revisionId를 바꾸지 않는다.

홈의 학습 후보는 사용자가 직접 구독한 대상의 활성 PUBLIC 퀴즈만 포함한다. 기본 필터는 전체이며 MVP에서는 해시태그 하나만 선택한다. 태그 선택지는 이 공개·구독 범위의 퀴즈에서 추출한다. 구독 개발자 기준 조회도 같은 범위를 지킨다. 선택 태그가 있으면 후보와 태그의 교집합을 사용하고 quizId로 중복을 제거한다. 태그 변경은 Subscription을 변경하지 않는다.

다음 문제는 선택 태그를 유지하며 완료 Attempt가 없는 quizId를 제공한다. 태그를 바꿔도 완료 기록을 유지한다. 미풀이 후보가 소진되면 완료된 퀴즈를 새 Attempt로 다시 풀거나 다른 태그를 선택할 수 있다. 후보 자체가 없으면 다시 풀기 대신 탐색·구독과 다른 태그 선택을 안내한다. 공개 범위·구독 변경·삭제 시 다음 조회와 풀이 시작에서 후보 적합성을 다시 검사한다. 답안 제출 시에도 현재 공개 범위·삭제 상태를 재검사한다.

하루 문제 수 제한과 당일 선정 고정은 제거한다. 선택 태그와 정답 여부에 관계없이 퀴즈를 1개 완료하면 그날 연속 학습 조건을 충족한다. 1단계는 Mock 상태로 재현하고 2단계는 완료 기록과 `(userId, learningDate)` 유일성으로 학습일을 한 번만 집계한다. 다시 풀기도 새 기록으로 보존하며 BugCoin 중복 보상 정책을 우회하지 않는다.

### 방문자 홈 체험

방문자 홈은 개인 학습 흐름과 분리된 `guestQuiz`/`guestAnswer` 타입 API를 사용한다. 브라우저 Mock 어댑터는 읽기 전용 공개 후보를 서비스의 랜덤 선택·채점으로 전달하며 사용자 상태를 저장하지 않는다. 결과는 해당 화면의 mutation 상태에만 존재한다. 데모 선택은 URL의 명시적인 `user`로 헤더와 본문을 함께 전환하고 개인 Attempt를 새로 시작한다. 사용자별 구독·채점·보상 규칙은 기존 서비스를 유지한다.

### 사용자별 스트릭 시간대

최초 접속에서 브라우저 IANA 시간대를 감지하고 저장된 사용자 설정이 있으면 이를 우선 사용한다. 감지 실패 시 Vercel IP 기반 시간대 제공 여부를 검토한다(이 경로만 별도 서버 조회가 필요할 수 있다). 국가 코드만으로 시간대를 결정하지 않는다. 확인할 수 없으면 명시적인 기본 시간대를 적용하고 마이페이지에서 변경하도록 안내한다. 기본값과 IP 제공 경로는 미결정이며 새 라이브러리를 전제하지 않는다.

신규 문제·다시 풀기를 정답 여부와 무관하게 하루 1개 이상 완료하면 사용자 시간대의 해당 날짜를 학습일로 인정한다. 같은 날짜는 한 번만 집계한다. 1단계는 브라우저 상태로 검증하고, 2단계는 서버 UTC 완료 시각과 저장된 사용자 시간대로 학습일을 계산한다. 시간대 변경으로 과거 기록·지급 보상을 소급 변경하지 않도록 완료 시점의 시간대와 학습일을 보존한다. 2단계는 브라우저 시간대를 보상 보안 근거로 신뢰하지 않으며, 시간대 변경에 따른 일일 보상 중복 방지를 별도로 검증한다. 날짜 유일성만으로 보상 악용 방지가 완성된 것으로 보지 않는다.

## 4. HTTP 계약

### 비공개 전환·삭제와 답안 제출

작성자의 PUBLIC→PRIVATE 전환 또는 삭제 즉시 구독 학습 후보에서 제외한다. 삭제는 `deletedAt`을 기록하는 soft delete이며 일반 조회·목록·재풀이에서 숨긴다. 타인의 진행 중 답안 제출은 `409 QUIZ_UNAVAILABLE`로 거부하고 이용할 수 없음을 안내한다. PRIVATE는 작성자만 계속 이용할 수 있고 삭제된 퀴즈는 작성자도 제출할 수 없다. 차단된 제출은 채점·완료 처리·보상을 만들지 않는다.

완료 Attempt와 이미 획득한 스트릭·XP·BugCoin 원장은 삭제·비공개 전환으로 취소하지 않는다. 완료 기록은 문제 본문을 숨긴 상태로 유지할 수 있어야 하며, 퀴즈 삭제가 Attempt·성과의 연쇄 삭제를 일으키지 않게 한다. XP 보존은 전체 제품 규칙이며 1단계에 XP 기능을 추가하는 근거가 아니다.

1단계 Mock API는 진행 중 비공개·삭제에 따른 제출 거부와 기록 유지 UX를 재현한다. 2단계는 상태 변경과 답안 제출을 같은 퀴즈 기준으로 직렬화하거나 동등한 동시성 제어를 적용한다. 상태 변경이 먼저 확정되면 제출을 거부하고, 완료가 먼저 확정되면 그 완료 기록과 성과를 유지한다.

## 5. 2단계 Spring Boot·인증·거래

Spring Boot(Java 21) Controller는 위 REST 계약을 구현하고 Service가 퀴즈·구독·풀이·BugCoin 규칙을 담당한다. Spring Data JPA와 MySQL 8.4는 실제 데이터·트랜잭션을 담당한다. 클라이언트가 보낸 userId·ownerId를 신뢰하지 않고 검증된 JWT에서 내부 User ID를 찾는다. Google OAuth2에서 검증한 계정의 불변 식별자를 내부 User에 유일하게 연결한다. JWT 만료·갱신·폐기 방식은 2단계 착수 전에 결정한다. 더미 사용자 상태를 실제 계정으로 자동 이전한다고 가정하지 않는다.

구매는 잔액 확인→BugCoin 차감→구매 기록→보관함 추가를 한 MySQL 트랜잭션으로 처리한다. 잔액 부족이면 전부 거부한다. 재전송과 동시 요청은 요청 키·유일성 제약·잠금 또는 동등한 방법으로 한 번만 차감·구매되게 한다. 장착은 보관함 소유를 검사한다. 관리자 상품 등록은 실제 권한을 검사한다. PG·현금 결제와 AI 상품 생성·주기 스케줄러는 범위에 없다.

## 6. 검증·배포·미결정 사항

- 1단계 Jest·React Testing Library: 입력 글자 수·코드 블록·퀴즈 1~5개·개별/일괄 저장·구독 조건·학습 태그·다음 문제·다시 풀기·하루 1개 완료 조건·BugCoin 구매/장착 UX. Playwright: 더미 사용자로 생성→저장→풀이→구독→태그 변경·다음 문제·다시 풀기→구매→장착 E2E. Vercel 배포에서 Mock API와 화면을 확인한다.
- 2단계: Spring Boot 서비스·REST 계약·MySQL 통합 테스트로 Google OAuth2·JWT·내부 User ID 소유권, 저장 복원, 학습일 중복 집계 방지, 중복 구매·BugCoin 차감의 원자성을 확인한다. 1단계 테스트 통과를 실제 보안·영속성 검증으로 간주하지 않는다.
- 확정: 1단계 Next.js·TypeScript·Mock API·더미 사용자·Jest·Playwright·Vercel, DB·실제 인증 제외. 2단계 Spring Boot·Java 21·MySQL 8.4·Spring Data JPA·Google OAuth2·JWT·실제 REST API.
- 미결정: 실제 AI 제공자·연동 시점, 문제 형식, 시간대 미감지 시 기본 시간대 값·Vercel IP 시간대 제공 가능 여부·시간대 변경 전후 일일 보상 중복 판정 세부 기준, JWT 만료·갱신·폐기, 더미 데이터 이전 여부, BugCoin 지급량, 2단계 배포 환경과 MySQL 호스팅. Kubernetes는 별도 실습 환경이다.

3D 데스크(P08-3D)는 React 편집 UI → Three.js 렌더러/OrbitControls/TransformControls → 타입 transformEquipment API → Mock 서비스 검증 → 사용자별 저장 순서다. 렌더러는 카메라·모델 표시·입력 좌표 변환을 담당하고, 배치 제약은 순수 `desk-spatial.ts`를 UI와 서비스에서 공유한다. 키보드·모니터·소품은 상판의 자식 좌표이며 책상 이동·회전 시 함께 변환된다. 기존 2D 배치는 읽기 시 호환 변환하고 구매 기록을 유지한다. 상세 계약은 API.md의 3D 데스크 배치 절을 따른다.

### 내 데스크와 상점 렌더링

`/my`는 현재 더미 사용자의 보관함과 배치 편집을 제공하고, `/shop`은 이웃 섹션/메뉴 없이 잔액과 상품 목록을 먼저 보여주고 미보유 상품에만 장착해 보기 버튼을 표시한다. 가격 아래 장착해 보기·구매하기를 가로 배치하며 보유 중 표시는 구매 버튼 위치를 유지한다. 해당 모달에서 임시 데스크 미리보기를 제공한다. 모달은 열 때의 equipment/transforms 스냅샷을 유지하고 별도 preview 오브젝트를 추가 렌더한다. 기존 책상·상품의 앵커와 추가 상품 앵커를 분리하므로 책상 미리보기 이동이 원래 공간을 이동시키지 않는다. 기존 공간과 추가 오브젝트를 각각 로컬 편집기로 관리한다. 픽셀 선택 맵은 추가 오브젝트를 별도 식별자로 구분하여 같은 카테고리의 기존 상품과 혼동하지 않는다. 기존 책상/상품도 선택·이동·회전 가능하며 기본 책상도 로컬 편집할 수 있다. 미리보기 자체는 API 변경을 호출하지 않고 실제 장착도 추가 대상만 저장한다. 기존 공간의 임시 변경은 모달 종료 시 폐기한다. 미리보기의 소품/버그리/추가 상품 레이어는 열 때의 책상 좌표 기준을 고정하고 현재 책상의 이동·회전을 역변환으로 상쇄하여 책상만 독립 조작한다. 저장 좌표는 책상 기준을 유지한다. 내 데스크는 transformDesk 요청으로 기본/장착 책상을 독립 이동하고, 서비스가 다른 아이템의 좌표·회전을 새 책상 좌표계로 보정해 같은 상태 쓰기로 저장한다. 렌더링 중에도 같은 순수 좌표 보정 함수를 적용해 저장 전후 위치를 유지한다. 모달의 상품 선택 버튼은 제거하고 초기화만 제공하며, 초기화는 두 로컬 편집기와 시점·확대 비율을 모달을 열었을 때 상태로 복구한다. 미리보기와 내 데스크에서 Canvas와 선택 조작 DOM을 함께 감싼 뷰포트에 비수동 wheel 리스너를 연결해 기본 스크롤을 차단하고 deltaMode를 정규화해 자동 맞춤 배율에 0.5~2.5 사용자 배율을 곱한다. 회전 버튼/드롭다운 위에서도 동일한 wheel 처리로 이어지며 뷰포트 밖 스크롤은 가로채지 않는다. 엔진 해제 시 같은 뷰포트에서 리스너를 제거한다. 드래그 중 확대 변경은 무시하며 이동 계산과 픽셀 선택은 실제 적용 배율을 사용한다. Canvas의 Home/PageDown/PageUp 키로 접근 가능한 상품 선택을 제공한다. 배경은 환경 미리보기로 전환한다. 실제 저장의 카테고리당 하나 계약은 유지하고 해당 경우 교체 버튼을 표시한다. 명시적 구매/실제 장착만 기존 mutation을 사용하고, 닫기·사용자 변경 시 미리보기를 폐기한다. 상점 모달은 내 데스크와 같은 Canvas 너비를 사용한다. 선택 상품의 임시 위치·회전은 useSpatialEditor를 통해 로컬 상태에 유지하고 모달을 닫으면 폐기한다. 상품 클릭 시 선택 테두리와 모서리 위 작은 회전 화살표를 표시하고 상품 드래그는 이동, 빈 공간 드래그는 시점 회전으로 처리한다. 내 데스크도 같은 직접 조작을 사용한다. Zdog의 동일 장면을 별도 Canvas에 카테고리 색으로 렌더해 실제로 보이는 픽셀을 hit-test하므로 상판에 가려진 상품을 선택하지 않는다. 명시적 겹침 순서는 `DeskOrder` 배열(뒤→앞)로 보관하며 메뉴 조작 시 `reorderDesk`로 원자적으로 저장한다. 순서를 지정한 장면은 각 오브젝트의 3D 투영을 유지한 채 같은 순서로 Canvas와 선택 맵을 합성한다. 기본 빈 순서는 기존 깊이 정렬을 유지한다. 뒤에 가려진 선택 대상의 테두리는 단독 선택 맵으로 구하지만 실제 클릭 맵은 가림을 그대로 유지한다. 미리보기에서 기존 아이템의 순서는 로컬 상태에만 두며, 새 상품 장착 시 저장된 기존 아이템 상대 순서를 유지하면서 추가 대상의 위치만 삽입한다. 선택 UI는 별도 DOM 레이어로 표시하며 읽기 전용 공개 공간에는 연결하지 않는다. 실제 장착 시 기존 equip 이후 transformEquipment를 호출하며, 후자의 실패는 부분 성공으로 안내하고 재시도 초안을 유지한다. 두 호출을 원자적 거래로 보장하지 않는다. 이전 `/shop/zdog`는 `/my`로 redirect한다. Canvas 입체 모델을 카드·내 데스크·공개 데스크에 공유하며 WebGL 컨텍스트를 만들지 않는다. 상품의 `transformEquipment` 계약은 유지한다. 버그리는 상품 카테고리와 별개인 `DeskObject.BUGRI` 편집 대상으로 선택 맵에 포함한다. `DeskTransforms.BUGRI`가 없으면 기본 좌표를 사용하며 전용 `transformBugri` mutation으로 저장한다. Mock은 현재 사용자 데이터만 쓰고 공개 프로필은 저장 좌표를 읽기 전용으로 제공한다. 배경 테마는 전체 Canvas 배경, 큰 입체 방, 가구/버그리 색상 조명을 함께 적용하고 방은 가구 뒤 레이어에 유지한다. 선택 맵은 조명 적용 후에도 독립 색으로 렌더한다. 쿼리의 `user`는 1단계 더미 사용자 선택값이며 실제 인증/인가가 아니다. 공개 페이지에는 편집 콜백을 연결하지 않는다.

키보드·모니터·소품·버그리의 상판 드롭은 드래그 시작 시 대상 모델의 바닥 원점과 포인터의 화면상 간격을 저장하고, 이동 중 접점을 현재 카메라/배율/중심 보정의 역투영으로 상판 평면과 교차시킨다. 기존 아이템은 해당 앵커, 추가 미리보기는 별도 previewAnchor를 사용한다. 받침이 상판 밖이면 직접 포인터 드롭도 검사한다. `desk-surface.ts`는 현재 책상의 이동·회전을 반영해 표면 범위를 확인하고 카테고리별 받침 크기 및 책상 대비 회전각으로 지지 여백을 확보한 뒤 저장용 아이템 좌표계로 변환한다. 실제 이동 중 초안에 반영하고 놓을 때 확정하며 기존 `transformEquipment`/`transformBugri` 저장과 미리보기 로컬 편집을 그대로 사용한다. 단순 클릭·취소·회전에는 적용하지 않는다. 좌표·높이를 함께 갱신하므로 화면 겹침 순서와 무관하게 카메라 회전 후 접촉을 유지한다.

빈 배경의 수평 드래그는 장면의 가까운 쪽이 포인터를 따라 움직이도록 yaw에서 수평 이동량을 뺀다. 상하 드래그는 pitch에 세로 이동량을 더해 가까운 쪽이 포인터를 따라 움직이게 한다. pitch 범위는 -85~85도이며 정면 아래도 허용한다. 아래에서 볼 때는 상판 위/아래 그룹의 그리기 순서를 역전해 상판 가림을 유지한다. 수동 겹침 순서는 그대로 우선한다. 정면 부근 수평 이동의 역투영 분모는 0에 가까워지지 않도록 제한하고, pitch<=0에서는 상판 윗면 스냅을 하지 않는다. 카메라 방위각과 높낮이 각도는 스크린리더 상태로 제공한다.

배치 편집으로 장면이 축소되지 않도록 자동 맞춤의 radius/height/center는 상품 구성별로 한 번 계산해 보관한다. 구성 키는 책상·키보드·모니터·소품 ID와 추가 미리보기 ID이며 transforms·선택·저장 재조회는 키에 포함하지 않는다. 실제 상품 구성이 바뀌거나 뷰어를 새로 열고 초기화할 때만 범위를 다시 계산한다. 휠 배율과 화면 크기/카메라 각도에 따른 투영은 이 기준 범위를 사용하므로 드롭 후 배치 범위 변화로 자동 축소·중심 이동하지 않는다.

정면 부근(-20~20도)의 아이템 MOVE는 드래그 시작 시점의 카메라 깊이를 유지하는 수직 평면에서 계산한다. 세로 입력은 cos(pitch)로 역투영해 높이를 변경하고 가로 입력만 X/Z에 반영한다. 해당 구간의 상판 스냅은 이동 중과 드롭 모두 생략한다. 책상은 기존 바닥 평면 이동을 유지한다.

기본 비스듬한 시점을 포함한 ±45도에서는 최초 유효 이동이 세로 우세이면 공통 vertical 드래그 평면을 선택한다. ±20도에서는 기존대로 항상 수직 평면이다. 선택한 평면은 pointerUp/cancel까지 고정하며 모든 비책상 SpatialTarget에 동일 적용한다. 수직 드래그로 내리거나 상판 높이 이상에서 시작했다면 상판 스냅을 생략해 높이 조절을 방해하지 않는다. 낮은 위치에서 상판으로 올리는 기존 접점 스냅은 유지한다.

배경 환경은 Canvas 2D 소프트웨어 원근 투영으로 렌더한다. 사각형의 네 벽을 기준으로 카메라 쪽 가까운 벽을 열고, 인접 벽의 열린 끝은 화면 밖까지 연장한다. 대각선은 두 벽, 정면 근처는 뒤쪽 벽과 양옆 벽으로 보이게 하여 축소 시 앞쪽 모서리가 추가로 꺾여 들어오지 않게 한다. near plane에서 면을 잘라 화면을 채운다. 수직선은 평행하게 유지하는 2점 원근을 사용하며 yaw/pitch는 가구와 동일하다. 환경을 역회전으로 고정하지 않는다. 배경은 별도 Canvas에서 그린 뒤 destination-over로 가구 뒤에 합성하고 바닥색으로 빈 영역을 채운다. 프레이밍 중심을 기준으로 방 구도를 잡고 화면 크기와 자동 맞춤 배율로 방 범위를 계산한다. 사용자 휠 배율은 방 크기·카메라 거리 계산에 포함하지 않고 가구와 같은 투영 배율로만 적용해 창문·벽·가구가 함께 확대/축소되도록 한다. 배경이 있는 장면은 `zdog/projection.ts`의 동일한 2점 원근을 방·가구·러그와 선택 맵에 적용한다. Zdog의 월드 변환·정렬 이후 렌더 경로를 투영하며, 상품 기준점과 선 굵기도 같은 깊이 배율을 사용한다. 바닥/상판 드롭은 포인터를 해당 높이 평면으로 역투영하고 세로 드래그는 시작 깊이를 고정한다. 저장 좌표와 상품 모델은 유지하고 배경 없는 장면·상품 썸네일은 기존 투영을 사용한다. 원근으로 커지는 앞쪽 러그를 위해 배경 장면의 기본 맞춤에 여유를 두되 사용자 배율과 방 크기는 별개로 유지한다.

창문은 기존 Zdog 모델을 투명 텍스처로 만들고 벽 평면의 역투영으로 샘플링해 이음선 없이 그린다. 두 테마의 창틀·달/별 자산을 재사용한다. 상품 카드의 고정 방 모델은 기존 Zdog 모델과 벽/바닥 경계를 유지한다.

공간 프레이밍은 책상·버그리·기존 상품·추가 미리보기의 수평 외곽을 각 아이템 회전과 itemFrame을 반영한 월드 좌표로 수집한다. 이 구성 범위의 중심과 반경을 최초 열기/구성 변경/초기화에 보관하고, 각 방위각에서 투영된 좌우 끝점의 중간을 카메라 중심으로 보정한다. 드래그/저장 중에는 보관된 범위를 유지하므로 카메라 추종이나 자동 축소가 생기지 않는다. 상판 역투영도 같은 보정 중심을 사용한다.

선택 맵은 불투명한 식별색의 채널 오차가 2 이하인 경우도 동일 오브젝트로 판정한다. 작은 모델 가장자리의 안티앨리어싱 반올림을 수용하되 중간 혼합색·투명 픽셀·배경은 계속 선택하지 않는다.

실제 공간의 방은 좌우·앞뒤 폭을 같게 하고 환경 그룹의 수평 중심을 매 프레임 가구 프레이밍 중심과 맞춘다. 러그도 방 중심에 놓아 최소 배율에서 배경과 가구의 중심이 어긋나지 않게 한다. 상품 썸네일에는 기존 고정 경계를 유지하며 저장된 아이템 좌표는 변경하지 않는다.
- 개발자 공개 목록: `/developers/[publicId]/quizzes` → TanStack Query → typed API `developerQuizzes/developerTags` → 공개 목록 서비스. 브라우저 Mock은 사용자별 구독과 전체 작성자의 저장된 공개 상태를 읽으며, HTTP 전환은 GET `/developers/{publicId}/quizzes` 및 `/developers/{publicId}/tags` 계약을 사용한다. 작성자 CRUD·전체 프로필/데스크와 독립된 공개 퀴즈·태그 조회 화면이다.

## 비로그인 홈 체험 — 문서 합의, 구현 별도

PRD AC-05h~i와 [페이지 구조](PAGE_STRUCTURE.md)의 방문자 정책을 따른다. 기존 구독 기반 학습·사용자별 Attempt·학습일·보상 설명은 로그인 사용자(1단계 더미 사용자) 대상이다. 비로그인 방문자는 전체 활성 PUBLIC 퀴즈의 랜덤 풀이·제출 후 해설·다음 문제만 체험하고 개인 기록·스트릭·보상을 남기지 않는다. 익명 소유권이나 더미 사용자 계정에 방문자 기록을 저장하지 않는다.

기존 사용자 기반 API 계약이 이 방문자 기능을 이미 지원한다는 의미는 아니다. 구현 시 별도의 방문자 조회·채점 계약과 제출 전 정답 비노출, 제출 시 공개·삭제 상태 확인을 정의해야 한다. 이번 문서 변경에서는 DTO·엔드포인트·코드를 추가하지 않는다. 1단계 실제 인증·서버 영속성 제외 정책은 유지한다.

### 공개 프로필 자기소개·링크

`DeveloperScreen`의 공개 프로필 모드에서 `ProfileAbout`을 사용자 정보와 데스크 사이에 배치한다. 본인 편집은 `ProfileAboutForm` → 폼 상태 훅 → Query API 훅 → typed client → Mock 서비스로 연결한다. `UserState.profileAbout`은 선택 필드여서 기존 v1 저장과 호환된다. 공개 조회는 자기소개·링크만 반환하며 다른 개인 상태는 포함하지 않는다. Markdown 렌더링은 원시 HTML을 실행하지 않는다. 공통 MarkdownEditor에 문맥별 placeholder prop을 추가해 기존 학습 입력을 유지한다.

`ProfileAbout`은 공개 프로필 정보 묶음의 공개 ID와 방문자 구독 동작을 ReactNode로 받아 소개와 함께 조립한다. 편집 상태·조회 오류·포커스 복귀는 같은 경계에 두며 사용자/로그인 상태 key로 초기화한다. 본인 편집 동작은 같은 styles.ts의 보조 액션 스타일, 외부 링크는 ProfileLinkIcon과 별도 링크 스타일을 사용한다. API·저장 데이터 계약은 바꾸지 않는다.

프로필 편집은 MarkdownEditor의 선택형 compact 밀도 및 Dropdown/TextField의 선택형 숨김 라벨을 사용한다. 다른 호출자의 기본 UI는 유지한다. useProfileForm은 필드별 오류를 보존하고 행 삭제 시 인덱스를 재연결하며, validationAttempt로 저장 검증 시에만 첫 오류 포커스를 요청한다.

### 공개 프로필 스트릭

공개 프로필은 홈 StreakSummary와 ActivityPeriods를 재사용한다. publicId가 주어지면 publicLearningDay typed API와 publicId별 TanStack Query 캐시로 주인의 공개 집계만 조회한다. 개인 learningDay와 같은 서비스 계산을 사용하며 공개 조회에서는 Mock 시간대 초기화·마이그레이션·저장을 하지 않는다. 시간대 미설정은 오류 상태로 유지한다. 공개 화면은 행동 촉구 대신 주인의 현재 학습 상태를 설명한다.


### 내 데스크와 장착 미리보기 공통 조작

`EditableDeskScene`이 직접 조작·휠 확대·접근성 출력을 공유하고 `sceneKeyDown`이 캔버스 내 선택 이동을 공유한다. 내 데스크의 포인터 완료는 즉시 저장하고 키보드 초안은 Enter 저장/Escape 취소를 유지한다. 평소 아래 조작 패널은 없으며 저장 상태는 스크린리더 전용, 실패 재시도·취소는 실패 시에만 표시한다. 보유 상품 목록은 유지한다.
