# PROFILE-LAYOUT UX 리뷰

## 대상과 변경 범위

- 사용자는 앞선 두 UI/UX 평가의 전체 수정을 승인했다. 개발자가 자기소개·작업물을 공개하고, 방문자가 이름→소개→외부 링크를 읽으며, 본인은 편집으로 진입하는 흐름을 검토한다. 사용자 특성은 검토용 가설이다.
- 이름/ID/소개/링크 묶음, 동일한 보조 편집 동작, 16px 본문, 정보 영역 폭 제한, 서비스 아이콘·외부 링크 구분을 개선한다. 기타 이름은 사용자가 입력한 데이터라 임의로 바꾸지 않고 실제 도메인을 함께 보여준다. 저장/API·데스크 캔버스·퀴즈/활동 영역은 변경하지 않는다.
- 워크트리 `자기소개`, 기준 커밋 `113a25a` 이후 미커밋 PROFILE-LAYOUT. 1280×900 및 390×900 화면을 확인한다.

## 사용자 지적과 구현 처리

| 문제 | 처리 |
| --- | --- |
| 이름·ID·자기소개·링크의 묶음 약함 | 하나의 공개 프로필 정보 영역에 소개까지 16px, 소개→링크 12px 간격 적용 |
| 편집 버튼이 정보 흐름을 가름 | 데스크톱 우측 상단, 모바일 소개·링크 뒤로 관리 그룹 분리 |
| 자기소개가 작음 | 본문 16px/28px, Markdown 제목은 별도 위계 유지 |
| 편집 동작 위치·형태 불일치 | 프로필 편집과 데스크 편집을 동일 높이·글자·배경·강조로 한 줄 배치 |
| 버튼이 콘텐츠보다 강조됨 | 테두리·그림자·버튼 이동 효과 제거, muted 보조 동작 |
| 넓은 화면에서 과도한 시선 이동 | 상단 정보 묶음 최대 896px, 본문과 관리 동작 사이 24px |
| 링크 목적지 불명확 | 종류별 정확한 서비스명과 아이콘, 기타는 사용자 이름+실제 도메인 |
| 외부 링크와 편집 버튼이 비슷함 | 외부 링크는 밑줄·아이콘·↗, 새 탭 스크린리더 레이블 유지 |

위 목록은 사용자 후속 요청에 대한 수정이며 독립 리뷰어가 발견한 문제로 기록하지 않는다. 독립 R0 결과는 아래에 추가한다.

## 독립 R0 — 새 컨텍스트 리뷰

- 리뷰어 `/root/profile_layout_review`, 제공된 PC/모바일 캡처를 먼저 본 뒤 최신 production `127.0.0.1:3158`을 Playwright로 직접 조작했다. 코드·문서 수정 없음.
- 첫 이해: 타입 개발자의 소개·작업물을 확인하는 공개 프로필. 방문자 진입→데모 로그인→소개/기타 링크 3개 입력→저장 및 변경→취소 확인→변경 취소를 직접 추적했다.

| 관점 | 판단·근거 |
| --- | --- |
| 목적/대상 식별 | 이름·ID 및 이어지는 소개로 대상 식별 |
| 정보 우선순위·첫 화면 | PC/모바일에서 소개·링크가 데스크보다 먼저 발견됨. 긴 소개도 순서 유지 |
| 핵심 행동·이동 단계 | 공개 화면→폼→저장, 링크 밑줄·아이콘·외부 화살표 확인 |
| 중복·밀도 | 편집 2동작 같은 강조. 모바일은 콘텐츠 뒤. 빈 소개 컨테이너 없음 |
| 상태·피드백 | 저장 안내·미저장 취소 확인·저장/취소 후 포커스 복귀 직접 확인 |
| 모바일·키보드 | 390px 긴 소개/링크 3개 가로 넘침 없음. 도메인 읽기 PL-UX-01 발견. 전체 키보드 순회 미확인 |
| 방문자·본인·타인 | 방문자 로그인/구독, author 편집 2동작, friend 구독이며 편집 없음 직접 확인 |

| PL-UX-01 | 390px 긴 기타 이름 뒤 example.com이 example.co / m으로 분리. 도메인은 aria-hidden | 일반 P2. 실제 목적지 판독 저하 및 보조기술 정보 누락 | 짧은 도메인 통째 줄바꿈, 긴 도메인 overflow 방지, 접근성 이름에 도메인 포함 | 수용. 도메인 inline-block/max-w-full, aria-hidden 제거. 기타 링크 E2E 이름을 추가 정보에 맞춰 갱신 | R1 해결 |

## R1과 종료

- C1/R1 수정 1회. 같은 독립 리뷰어가 최신 production 3158에서 로그인→편집→링크 2개 입력→저장을 직접 수행했다.
- 390px 긴 기타명 뒤 example.com이 다음 줄의 한 덩어리로 표시되며 텍스트 영역 1줄을 확인했다. 63자 호스트+.example.com은 내부 줄바꿈하며 가로 넘침 없음(390/390px).
- 두 링크의 접근성 이름에 지정 이름·실제 도메인·새 탭이 포함됨을 확인했다. PC 1280px도 소개→링크 순서와 우측 보조 편집 동작·도메인 표시를 유지하고 가로 넘침 없음(1280/1280px).
- 캡처 `/tmp/profile-review-r1-mobile.png`, `/tmp/profile-review-r1-pc.png`. PL-UX-01 해결, 새 문제 없음. 필수 미해결 없음으로 종료한다.
- R0 7관점 판단을 유지하며 도메인 판독·접근성 누락을 보완했다. 스크린리더 실기·외부 사이트 도착·저장 실패/재시도·모든 아이콘 실제 화면·전체 키보드 순회는 미확인이다. 기존 기능 E2E와 최종 전체 verify는 별도 검증이다.

## 사용자 후속 피드백 — 저장 완료 토스트

사용자가 저장 완료 문구를 본문 대신 토스트로 표시하도록 요청했다. 독립 리뷰어 발견으로 기록하지 않는다. C2에서 본문 상태 문구와 빈 소개 컨테이너 생성 조건을 제거하고 기존 DeveloperScreen의 공통 Toast를 사용한다. 저장 토스트는 4초 자동 닫힘/직접 닫기이며 다른 알림으로 교체되면 이전 타이머를 해제한다. 최종 검증 1차는 이 후속 요청으로 lint 단계에서 중단(SIGTERM)했으므로 성공 근거로 사용하지 않는다. 변경 후 관련 검사와 전체 검증을 다시 수행한다.


## C2/R2 — 토스트 재검증

같은 리뷰어가 최신 production에서 390px·1280px 저장을 직접 수행했다. 하단 고정 토스트(position fixed, 900px 화면 하단25px), 약4초 자동 닫힘·직접닫기, 소개 내부 성공문구/알림 여백 부재와 저장 후 프로필 편집 포커스 복귀를 확인했다. 새 문제 없음. 캡처 `/tmp/profile-review-r2-390.png`, `/tmp/profile-review-r2-1280.png`.

## 사용자 배치 변경 — C3

사용자는 ‘학습자’ 제목 제거, 프로필 편집을 페이지 오른쪽 끝에, 데스크 편집을 데스크 위에 배치하도록 요청했다. 이전의 상단 폭 제한/두 편집 동작 묶음보다 최신 요청을 우선한다. 이름 제목 대신 공개 ID를 사용하고, 소개 폭만768px로 제한한다. 프로필 편집은 상단 우측 끝, 데스크 편집은 캔버스 위 별도 우측행이다. 이 변경 역시 사용자 요청이며 독립 리뷰어 발견으로 기록하지 않는다. R3에서 최신 배치와 토스트/기타 도메인 회귀를 확인한다.

## C3/R3 — 최종 배치 재검증

같은 독립 리뷰어가 learner 프로필을 390px·1280px에서 직접 확인했다. @bugri-learner만 표시되고 이름 제목 없음, 프로필 편집은 ID와 같은 상단행 오른쪽 끝, 데스크 편집은 데스크 바로 위 별도 우측행이다. 본인은 편집 2동작이 있고 로그인한 friend에게는 둘 다 없다. 저장 후 본문 성공 문구 부재·토스트 자동닫힘/직접닫기·편집 버튼 포커스 복귀·가로 넘침 없음도 확인했다. 캡처 `/tmp/profile-review-r3-390.png`, `/tmp/profile-review-r3-1280.png`.

C1/R1~C3/R3 수정·재검토 3회로 종료한다. 추가 문제 및 필수 미해결 없음. 도메인은 R1 직접 검증+최신 E2E 근거를 유지하며 R3에서는 다시 입력하지 않았다. R0에 기록한 스크린리더 실기·외부 사이트 실제 도착 등의 미확인 한계는 유지한다. 사용자 요청의 위치 변경은 초기 리뷰 평가보다 우선하며 초기 폭 제한·편집 그룹 유지 여부를 최종 결함으로 보지 않는다.

## 완료 전 후속 스크린샷 평가 요청

사용자가 최신 스크린샷에서 UX/UI 문제를 각각 목록화하도록 요청했다. 추가 구현 요청이 아니므로 코드 변경은 하지 않는다. 정적 화면에서 편집 동작의 클릭 가능성, 데스크 조작의 발견성, 아래 학습 콘텐츠의 발견 여부를 UX 검토 후보로 본다. 시각적으로는 링크→데스크 사이 간격, 캔버스 대비 오브젝트 비중, 옅은 편집 텍스트, 버튼 내부 패딩으로 인한 텍스트 끝/카드 끝의 정렬 차이를 개선 후보로 본다. 실제 hover/터치 조작이나 이용 목적이 필요한 판단은 가설이며 접근성 수치 위반으로 단정하지 않는다. 사용자 지정 버튼 위치·큰 데스크 정책을 자동으로 되돌리는 제안은 하지 않는다.
