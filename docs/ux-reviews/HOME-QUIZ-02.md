# HOME-QUIZ-02 헤더 너비 정렬과 디자인 재검토

## 사용자 요청과 범위

사용자가 768px 퀴즈 폭과 시각적 완성도를 거부했다. 홈 퀴즈 외곽은 헤더 콘텐츠 폭과 일치시키는 것으로 확정했다. 최초에는 너비 수정과 개선안 제시를 요청했으며, 후속 지시 ‘B로 ㄱ’에 따라 B 단일 열 디자인 구현까지 승인했다. 연속 학습은 다른 브랜치 소유이므로 영역과 자리 표시자를 수정하지 않는다. 직접 풀이 `/solve`의 기존 폭도 이번 홈 요청과 분리해 유지한다.

앞선 HOME-QUIZ-01의 기능·잘림 검사 통과를 시각적 완성도의 승인으로 해석하지 않는다. 사용자 불만을 새 검토의 입력으로 삼아 B안을 구현하고 실제 화면을 다시 검토했다.

## 구현과 측정

- `src/components/solving/solve-screen.tsx`: 홈의 `max-w-3xl` 제한 제거. 공통 ProductLayout의 너비를 그대로 사용.
- `src/app/page.tsx`: 보조 상점 링크도 같은 좌우선에 정렬.
- `ProductLayout`와 헤더는 `max-w-[1220px]`, `px-5 md:px-12`를 공유하는 기존 구성을 유지한다.
- 메인 Playwright 실측: 1440px에서 헤더·퀴즈 x=158~1282(1124px), 768px에서 48~720(672px), 390px에서 20~370(350px), 375px에서 20~355(335px). 모두 가로 넘침 없음.
- 메인 캡처 `/tmp/home-width-{1440,768,390,375}.png`. Node v22.23.3, 동일 워크트리 개발 서버 `localhost:3000`.

## 독립 UX 검토

새 컨텍스트 UX sub-agent가 방문자·학습자·제출 결과를 직접 조작하고 캡처를 확인했다. 1440/768/390/320에서 헤더 기준 정렬과 가로 넘침 없음을 확인했다. 연속 학습과 그 영역으로 인한 밀림은 평가에서 제외한다.

| 관찰 | 영향 | R1 개선 제안 |
| --- | --- | --- |
| 질문 전체의 진한 자동 포커스 테두리 | 질문이 편집 가능한 입력창처럼 보임 | 질문 접근성 초점은 유지하되 비조작 콘텐츠의 초점 표현을 따로 설계. 선택지·버튼 키보드 초점은 유지 |
| 제목·태그 라벨·선택기가 각각 다른 행 | 질문 전 세로 공간이 과도함 | PC는 제목 왼쪽/태그 오른쪽 한 행, 모바일 두 행 |
| 긴 선택지 테두리 안의 13px 텍스트 | 내용보다 빈 면적이 지배하는 설문 폼 비례 | 답안 15~16px, 높이52~56px, 내부 간격16px. 선택 상태 강조 |
| 주제와 질문의 블록 구분 약함 | 읽기 시작점이 불명확 | 주제는 낮은 강조의 배지, 질문 PC24px/모바일20~22px |
| 한국어 어절 중간 줄바꿈 | 모바일 읽기 흐름 저하 | 한국어 break-keep, 긴 코드·URL은 별도 넘침 처리 |
| 결과 배너·문제·답·해설이 길게 수직 나열 | 모바일 다음 행동이 멀어짐 | 짧은 결과 상태 행, 답안 요약 묶음, 해설 하위 배치 |

UX는 긴 답안·코드형에서도 읽기 순서가 안정적인 단일 목록을 추천했다. 두 열은 모든 문제에 강제하지 않는다는 절충을 제안했다. 기능 흐름의 동작과 시각 평가를 구분했다.

## 독립 UI 검토와 추천안

새 컨텍스트 UI sub-agent도 실제 1440/375 방문자·학습자·결과를 캡처해 확인했다. 정렬은 일치하지만 24px 질문/13px 답안 비례, 정적 콘텐츠의 입력창 같은 자동 포커스, 같은 흰 표면을 구분하는 과한 테두리, 큰 연두 결과 배너, 분리된 보조 링크를 시각 문제로 지적했다.

| 방향 | 구체 구성 | 절충 |
| --- | --- | --- |
| A 질문/답변 좌우 분리 | 카드 외곽 폭 유지, 질문52%·답변48%, 선택지 자체는 한 열. 질문 측 옅은 canvas, 답변 surface, PC32~36px/모바일20px 패딩 | 짧은 문제는 구성감이 좋아지지만 왼쪽 빈 면적이 생김. 긴 코드/설명은 상하 배치로 바꿔야 하므로 문제별 구조가 달라짐 |
| B 단일 열 학습지 — 추천 | 제목·필터 한 행, 카드 내부 주제→질문→답안→제출. PC32px/모바일20px 패딩, 질문24/36px·답안16/24px, 답안 높이56px·간격12px. 작은 상태 행→답안 비교→해설 | 가변 길이의 개발 퀴즈와 코드에 일관된 구조. 폭 축소 대신 글자·표면·여백 리듬 개선 필요 |

메인은 UX와 UI의 공통 추천인 B를 기본 방향으로 선택했다. A는 비교안으로 남기며 모든 문제의 좌우 분리를 강제하지 않는다. 짧은 예제에만 맞춘 장식을 추가하거나 새 브랜드·폰트를 도입하지 않는다. 포커스는 제거 대상이 아니라 자동/포인터 진입과 키보드 조작을 구분해 재설계할 대상이다. 최초 제안 단계에서는 너비 변경에 한정했으나 이후 사용자가 B 구현을 승인했다.

정적 시안 A: `/tmp/bugri-ui-review/proposal-a.html`, `proposal-a-1440.png`, `proposal-a-375.png`. 제품 화면이 아니며 기존 헤더 상세와 별도 소유의 연속 학습 영역은 생략한 비교용이다. 실제 화면 증거는 같은 디렉터리 `{guest,learner,result}-{1440,375}.png`다.

## 범위별 판단

- 너비 수정: 독립 UX/UI 실제 화면·반응형 확인 완료. 사용자 요구의 헤더 콘텐츠 좌우선 일치.
- 디자인 전체: A/B 제안 후 사용자가 B를 선택하여 C2에서 구현했다. 아래 실제 화면 재검증을 별도로 기록한다.
- 사용자 흐름: 리뷰어가 방문자/학습자 선택·제출·결과를 직접 확인. 장문 코드·오류·빈 상태·스크린리더 전수 검증은 이번 디자인 탐색에서 미확인.
- 회차: C1 너비 변경/R1 독립 검토 → 사용자 B 선택 → C2 B 구현/R2 독립 검토 → C3 포커스 보완/R3 독립 검토. 사용자 선택으로 범위를 확대한 것이며 sub-agent가 추가로 발견한 문제로 기록하지 않는다.

## C2 B 구현

- 홈 외곽은 헤더와 같은 너비, 학습 태그와 제목은 PC 한 행/모바일 두 행. 공통 Dropdown은 유지하고 배치만 해당 영역에서 조정한다.
- 공통 Card·Badge·Choice·Checkbox·Button을 재사용. 주제 배지→PC24px/모바일22px 질문→16px/56px 답안→144px 이상 주 버튼으로 비례를 조정한다. 로컬 Tailwind arbitrary variant를 `solving/styles.ts`에 두어 다른 화면의 공통 스타일을 덮어쓰지 않는다.
- 결과는 짧은 판정/날짜 행, 내 답·정답 비교면, 해설, 다시 풀기·다음 문제 순서. 보조 안내와 상점 링크는 PC 한 행/모바일 세로.
- 정적 질문의 입력창 같은 focus ring은 제거하고 실제 답안/버튼의 키보드 focus는 유지한다. 질문으로의 프로그램 초점/스크롤 이동은 보존한다. 늦은 최초 응답이 이미 사용 중인 다른 컨트롤 또는 열린 dialog의 초점을 뺏지 않도록 했다.
- 포커스 회귀 단위 테스트를 먼저 작성해 기존 구현의 실패를 확인한 뒤 수정했고 관련 단위 6개가 통과했다. 스타일 자체를 복제하는 테스트는 추가하지 않았다.
- 메인 실제 캡처: `/tmp/bugri-b-implemented-{1440,375}.png`, `/tmp/bugri-b-result-{1440,375}.png`. 원본 연속 학습 파일 diff 없음.
- 너비 전용 전체 검증은 B 승인 후 중단했다. 해당 결과는 B 코드의 검증 성공 근거로 사용하지 않는다.

## R2·R3 실제 화면 독립 검토

- UX 리뷰어: PC1440/모바일375의 방문자·학습자·오답 결과, 키보드 Tab/Space 선택, 다음 문제·재도전·모달 취소를 직접 확인했다. 필수 수정 사항 없음. R3에서 다음 문제·재도전의 질문 초점과 Escape 후 데모 트리거 복원을 재확인했다.
- UI 리뷰어: PC1440/모바일375의 문제·결과·방문자·선택 상태를 직접 확인했다. 16px 답안/56px 행, 헤더 정렬, 줄바꿈·넘침과 시각 위계를 확인했다. 선택지의 중복 focus ring을 선택 개선으로 제시했고 C3에서 외곽 ring만 제거했다. R3에서 native radio의 3px 키보드 표시와 Space 선택이 유지됨을 확인했다. 남은 필수 수정 사항 없음.
- C3은 최초 데이터 도착 때의 focus 처리를 `focusKey:hasResult`로 기록하여 StrictMode 재실행도 사용 중인 다른 컨트롤의 초점을 빼앗지 않게 한다. StrictMode 회귀 테스트의 의도한 실패를 확인한 뒤 수정했다. UX 리뷰어는 코드와 테스트를 검토했지만 지연 네트워크 상황을 브라우저에서 의도적으로 재현하지는 않았다.
- 메인 추가 측정: 격리 브라우저의 긴 코드/한국어/URL 선택지 fixture에서 모바일375, 문서 너비375, 코드 clientWidth293/scrollWidth3094, 선택지 너비293·16px 글자를 확인했다. 코드 내부에서만 가로 스크롤하며 답안은 줄바꿈한다. 앱 seed와 저장소 파일은 바꾸지 않았다. 스크린리더·오류/빈 상태 전수 검증은 하지 않았다.
- 관련 단위 2 suites/6 tests, 홈·풀이 E2E17개 통과. 마지막 C3 이후 관련 단위6개와 홈 E2E3개 재통과. 테스트 기대를 약화하지 않았다.
