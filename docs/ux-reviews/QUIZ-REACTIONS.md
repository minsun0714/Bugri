# QUIZ-REACTIONS 독립 UX·UI 리뷰

## 대상과 증거

- 목표: 문제를 풀고 해설을 확인한 더미 사용자가 개별 문제에 좋아요·싫어요를 선택·취소·변경한다. 사유·집계·추천은 제외한다.
- 구현: 이 워크트리의 미커밋 QUIZ-REACTIONS diff. 기존 Button과 토큰을 사용하고 사용자·quizId별 API/저장 경계를 유지한다.
- 새 컨텍스트 UX/코드 리뷰어 `ux_review`, UI 리뷰어 `ui_review`. 사전 시각 설계는 별도 `visual_design`이 수행했다. 리뷰어는 코드 수정·추가 위임을 하지 않았다.
- R0 증거: `/tmp/bugri-reactions/1280-selected.png` (1280×900), `390-selected.png` (390×900), `error.png` (1280×720), 모두 fullPage. 구현자 Playwright가 제출→선택→새로고침→변경→Enter 취소→재풀이→다음 문제 및 실패 재시도를 수행했다. `/tmp/bugri-reactions-e2e.log`: 3개 통과.
- 리뷰어는 캡처·조작 코드/로그를 간접 확인했다. 직접 브라우저 조작을 수행한 것으로 표현하지 않는다. R1 캡처는 같은 경로를 갱신하므로 R0 관찰은 아래 기록으로 보존한다.

## 최초 관찰과 흐름

두 리뷰어 모두 문제·결과·해설과 같은 카드에 평가가 있어 대상을 이해할 수 있고, 평가 후 계속 학습하는 화면으로 읽었다. 별도 화면·확인·사유 입력이 없다. 홈 달력이 첫 viewport를 크게 차지하는 기존 구조는 이번 수정 범위의 결함으로 분류하지 않았다.

## UX 관점별 평가

| 관점               | 판단       | 근거·한계                                                                                                                                                                       |
| ------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 목적·대상          | 문제 없음  | 같은 문제 카드의 해설 뒤에 평가가 연결된다.                                                                                                                                     |
| 정보 우선순위      | 문제 없음  | 해설보다 앞서지 않고 다음 문제보다 약하게 표시된다.                                                                                                                             |
| 핵심 행동·이동     | 문제 없음  | 제출부터 선택·취소·재풀이까지 제공된 실제 E2E 증거로 확인했다.                                                                                                                  |
| 중복·밀도          | 문제 없음  | 두 버튼만 추가하고 권유·집계·사유를 추가하지 않았다.                                                                                                                            |
| 상태·피드백        | 문제 없음  | 선택은 배경·테두리·체크로 표시하고 실패 시 기존 선택과 재시도 안내를 유지한다.                                                                                                  |
| 모바일·키보드      | UI-01 보완 | 390px에서 잘림 없음, Enter 취소 확인. R0 UX가 코드의 44px 선언만으로 높이를 인정한 부분은 UI 캡처 관찰로 문제를 발견하고 C1 E2E 실측으로 보완했다. 실제 Tab/음성 출력은 미확인. |
| 방문자·사용자 분리 | 코드 확인  | 방문자에는 컨트롤이 없고 사용자별 키·저장을 사용한다. 실제 전환 화면은 미확인, API 사용자 격리 테스트는 별도 실행했다.                                                          |

## UI 관점별 평가

정답→문제→답 비교→해설→평가→다음 문제 위계가 유지된다. 보조 버튼 글자·보라색 토큰·둥근 모서리는 기존 Button과 일치한다. 두 라벨은 모바일 한 행에서 읽히고 평가와 이동 행은 오른쪽 정렬된다. PC 실패 안내는 버튼 인접 위치에서 잘리지 않는다. 다크 테마·모바일 오류·로딩·실제 포커스 링은 미확인이다.

| ID    | 위치·관찰                                                                           | 영향·우선순위                                        | 개선·해결 조건                                       | 처리                                                                                                                            |

| UI-01 | R0 PC/390px 평가 버튼이 약38px로 보임. 로컬과 공통 sm 최소높이 선택자가 동일 특이성 | 일반 모바일 조작성. WCAG 24px 위반으로 주장하지 않음 | 두 버튼 실제 높이 ≥44px, 선택·비선택 유지, 겹침 없음 | C1: 로컬 선택자를 `[&.ui-button.sm]:min-h-11`로 강화하고 PC·모바일 bounding box 검증 추가. 메인도 리뷰 중 동일 원인을 발견했다. |

독립 코드 리뷰는 완료/이용 가능 검증, 단일 반응 교체·삭제, 실패 보존, 사용자별 캐시, 기존 저장 호환·손상 거부를 확인했으며 추가 결함을 발견하지 않았다.

## 회차

| 회차  | 변경                     | 결과                                                                                                  | 미확인                                        |
| ----- | ------------------------ | ----------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| R0    | 최초 구현                | UX 필수 문제 없음, UI-01 보완                                                                         | 직접 브라우저 조작·음성·다크·로딩·모바일 오류 |

수정 1회로 종료했다. 두 독립 리뷰어 모두 갱신된 캡처·조작 증거를 간접 확인했으며 필수 미해결·보류 문제는 없다. 선택 상태 높이는 캡처와 상태에 무관한 최소높이 규칙으로 확인했다. 실제 스크린리더·Tab 탐색·다크 테마·로딩·모바일 오류 상태는 이번 화면 리뷰에서 미확인이다.
