# QUIZ-REACTION-CARDS 독립 UX·UI 리뷰

## 대상과 근거

- 사용자 후속 요청: 목록 카드·제출 전 풀이 카드에도 평가 노출, 텍스트 대신 엄지 위·아래 아이콘, 아이콘 옆 반응 개수 표시. 선택·취소·변경, 사유 없음. 방문자는 집계 조회 후 명시적 데모 선택으로 평가한다.
- 사용자 선택만으로 평가를 자동 저장하지 않는다. 1단계 집계는 같은 브라우저의 더미 사용자 반응 합계다.
- 새 컨텍스트 `cards_ux`·`cards_ui`가 스킬과 리뷰 계약을 적용했다. 메인 구현과 분리한 캡처·코드·E2E 증거 리뷰이며 직접 브라우저 조작으로 표현하지 않는다. 별도 사전 시각 설계 `visual_design`의 Button/배치 기준을 적용했다.
- `/tmp/bugri-reaction-cards/{1280,320}-{tag,developer,profile,unsolved}.png`: viewport 각 너비×900, fullPage. `/tmp/bugri-reactions/{1280-selected,390-selected,error}.png`: 제출 결과·저장 실패. 캡처는 후속 실행으로 갱신되며 R0 아래 관찰은 집계 추가 전 버전이다.
- `/tmp/bugri-reaction-cards-icons-e2e.log` 6개 통과: 목록→평가→미제출 풀이 동기화, 재풀이·취소·변경, 방문자 모달 취소 포커스 복귀 및 자동 평가 없음. R0 리뷰는 이 아이콘 버전을 근거로 했다.

## R0 최초 관찰과 관점별 평가

두 리뷰어 모두 목록은 퀴즈 선택/평가, 풀이 화면은 답안 선택/제출/문제 평가로 이해했다. 제목 링크·이동 화살표와 평가가 형제로 분리되어 오작동 없이 목록에서 평가할 수 있다.

| 관점 | UX·UI 관찰 |
| --- | --- |
| 목적·대상 | 각 퀴즈 카드 안의 위·아래 엄지로 평가 의미와 대상을 이해한다. |
| 위계·첫 화면 | 제목·문제·답안이 먼저 보이고 평가는 오른쪽 하단 보조 행동이다. 320px 목록/직접 풀이 첫 카드에서 평가가 보인다. |
| 이동·행동 | 목록에서 선택한 반응이 제출 전 풀이에 이어지고, 별도 사유/확인 단계 없이 취소한다. |
| 밀도·여백 | 두 아이콘이 한 줄, 8px 간격을 유지한다. 작성자 링크/태그와 독립 영역으로 구분한다. |
| 상태·색상 | 선택은 채움·배경·테두리, 실패는 기존 선택 유지와 인접 오류로 표시한다. 색에만 의존하지 않는다. |
| 모바일·키보드 | 320px에서 넘침 없음. 44px 터치 높이, aria-label/pressed 유지. Enter 취소·Escape 후 포커스 복귀는 구현자의 실제 E2E 증거로 간접 확인. |
| 방문자·사용자 분리 | 방문자 명시적 선택·자동 저장 없음은 E2E 확인. 사용자/quizId 캐시와 사용자별 저장은 독립 코드 리뷰로 확인. |

R0 독립 코드 리뷰는 완료 조건만 제거되고 접근 가능 여부/값 검증이 유지됨, 사용자·문제별 캐시 격리, 방문자의 평가 mutation 미호출을 확인했다. 당시 방문자 조회 비활성 구조는 후속 집계 요청으로 읽기 전용 공개 조회로 변경되었다.

## 문제 목록과 처리

R0 당시 두 리뷰어는 필수 결함 0개로 판단했으나, 사용자 지적으로 제출 아래 배치 판단을 철회했다. 집계 추가는 리뷰어 지적이 아닌 사용자 후속 요구다. 이전 텍스트에서 아이콘으로 바꾼 것도 사용자 요청이며 리뷰어 발견으로 기록하지 않는다.

## 사용자 지적 후 재검토

- UX-01: 질문→답안→제출→평가 순서는 평가를 제출 후 행동처럼 보이게 하고 입력 영역의 경계를 흐린다. R0 리뷰가 동작/낮은 시각적 무게만으로 배치를 인정한 판단은 철회한다. 이 문제는 최초 독립 발견이 아니라 사용자 지적을 받은 후 두 리뷰어가 재검토한 결과다.
- C2: QuizPanel에 반응 슬롯을 추가하고 작은 제목과 같은 메타정보 헤더에 둔다. PC는 제목 오른쪽, 모바일은 제목 아래 같은 헤더 내부이며 질문 본문과 답안 폼은 전체 폭을 유지한다. 답 제출 아래 평가를 제거한다. 방문자·제출 결과도 같은 위치를 사용한다.
- 해결 조건: PC/320px 모두 평가가 답안 폼보다 위, 질문 읽기를 방해하지 않음, 제출은 답안 영역 마지막 행동, 제출 후에도 같은 메타정보 위치 유지.


### C2/R2 UX 직접 검증

Node v22.23.3 Playwright로 `http://127.0.0.1:3497`에서 독립 UX 리뷰어가 직접 조작했다. 320px에서 평가 하단 y374 < 첫 답안 y518 < 제출 y647. PC 작은 제목 오른쪽, 모바일 메타정보 안 줄바꿈 및 본문 전체 폭을 확인했다. 미제출 좋아요→숫자1→답 제출→결과 선택/숫자 유지, 하단 평가 중복 없음, 방문자 모달 Escape 후 초점 복귀를 확인했다. `/tmp/ux-r2-result.png`, `/tmp/ux-r2-desktop.png`. 집계·공개 접근 검증·guest 읽기 전용 경로에 독립 코드 리뷰 결함 없음. 긴 코드·큰 집계·음성 출력은 UX 직접 미확인, 연속 다음 문제는 기존 E2E 증거에 의존한다.


### C2/R2 UI 직접 검증과 종료

독립 UI 리뷰어는 같은 서버에서 1280×900 라이트·320×900 다크의 풀이/태그 목록을 직접 조작했다. 실제 좋아요0→1, 선택 채움, 약62.7×44px 버튼, 제출이 마지막 행동인 배치를 확인했다. `/tmp/ui-r2-1280.png`, `/tmp/ui-r2-320.png`, `/tmp/ui-r2-320-tag.png`. `/tmp/ui-r2-320-long-stress.png`는 DOM 표시만 긴 문구·양쪽1000으로 교체한 합성 스트레스 화면이며 실제 집계 증거가 아니다. 문서/화면 너비320px, 줄바꿈·숫자·제출 카드 내부 유지를 확인했다.

C2 검증 당시 종료 가능으로 판단했으나 사용자 후속 승인으로 하단 좌우 배치 C3를 수행한다. 최초 아이콘 변경 및 두 후속 수정은 사용자 지시이며 독립 리뷰가 선제 발견한 것으로 기록하지 않는다. 미해결 필수 문제 없음. 실제 스크린리더·모든 테마/페이지 조합·모든 오류 상태의 직접 재조작은 미확인이다.


## C3 — 사용자 최종 승인: 하단 왼쪽 평가·오른쪽 제출

사용자는 상단보다 왼쪽 아래를 선호했고, 같은 행 오른쪽 제출 제안을 명시적으로 승인했다. C2 상단 배치는 이 최신 지시로 대체한다. 최초 UX-01의 제출 아래 별도 평가 행으로 되돌리는 변경이 아니다.

AnswerForm 하단의 같은 flex 행에서 평가가 왼쪽, 제출이 오른쪽이며 결과 화면도 평가 왼쪽/다음 행동 묶음 오른쪽이다. 목록 평가 역시 왼쪽 정렬한다. 320px 정상 숫자는 같은 행, 큰 숫자/오류로 공간이 부족하면 평가 다음 제출이 오른쪽 정렬로 줄바꿈한다. 스크린리더 상태 요소에 의한 여백으로 생긴 4px 중심 차이는 space-y 대신 flex gap으로 수정했다. 좌표 허용치를 완화하지 않는다.

C2 코드의 전체 verify는 Node v22.23.3에서 단위310개·도구3개·E2E197개·lint·타입·빌드 통과(`/tmp/bugri-reaction-cards-final-verify.log`). C3 변경 이후 새 검증·리뷰가 필요하며 이전 통과를 C3 결과로 표현하지 않는다.


### C3/R3 직접 확인 및 최종 범위 정정

두 리뷰어가 Node22.23.3/Playwright로 1280 라이트·320 다크 화면을 직접 조작했다. 하단 평가/제출 중심 일치, 평가→답 선택→제출→결과→다음 문제의 선택·개수 보존/초기화, guest 모달 취소 초점 복귀를 확인했다. UX 증거 `/tmp/ux-r3-result-320.png`, `/tmp/ux-r3-desktop.png`. UI 증거 `/tmp/ui-r3-{1280,320}.png`, `/tmp/ui-r3-320-result-group.png`, `/tmp/ui-r3-320-tag.png`. `320-stress`와 `320-error-synthetic`은 DOM 합성 표시 검토이며 실제 집계·실패 재현이 아니다. 일반320px 한행, 큰숫자/오류는 평가 먼저·제출/결과행동 다음 오른쪽으로 겹침 없이 줄바꿈했다.

사용자는 이후 적용 범위를 명시적으로 정정했다: **풀이 퀴즈는 왼쪽 아래, 목록 카드는 오른쪽 아래**. 목록까지 왼쪽으로 확대한 것은 메인의 해석 오류다. 이 정정은 내부 리뷰에서 발견한 결함이 아니며, 풀이 R3 배치는 유지하고 목록 정렬만 복원하는 후속 표시 변경으로 검증한다. 앞선 목록 왼쪽 관찰은 최종 승인 방향이 아니다.


## 사용자 후속 범위: 목록 오른쪽 복원·관리 PUBLIC 카드 추가

- 최종 매핑: 풀이(로그인/방문자/결과)는 하단 왼쪽, 목록(태그/개발자/프로필/내 퀴즈 관리 PUBLIC)은 카드 오른쪽 아래다. 평가 컨트롤 기본 right, 풀이 호출자만 left를 명시한다.
- 요청 URL `/quizzes/authoring/manage?user=learner&status=PUBLIC`의 누락은 메인이 `src/components`만 찾아 `src/features/quiz-authoring/quiz-list.tsx` 사용처를 놓친 탓이다. PUBLIC 카드 footer에 동일 평가 컨트롤을 연결하고 PRIVATE/PENDING은 확장하지 않는다.
- 관리 카드 E2E는 읽기전용 seed에서 복사한 learner 소유 PUBLIC fixture로 정확한 경로를 검증했다. 관리 진입과 평가의 독립, 0→1, 새로고침 선택/집계 복원, 오른쪽 실제 좌표를 확인한다. API 생성 흐름 증거와 구분한다.
- 최신 `/tmp/bugri-reaction-manage-e2e.log`: PC1280/mobile320 포함 평가8개 통과. `/tmp/bugri-reaction-manage-regression.log`: 작성관리 관련4개 통과. 관련 단위21개·전체타입·변경 ESLint/Prettier·diff 통과.
- 정렬 복원 전 C3 빌드 `k5K4EsGaln1TCajaTBKU2`는 `/tmp/bugri-reaction-footer-final-verify.log`에서 전체 lint·타입·단위310개·도구3개·빌드·E2E197개 통과. 그 빌드 이후 차이는 화면별 정렬 prop, 관리 UI 연결 및 해당 테스트·문서이며 API/저장/집계/의존성/런타임은 동일하다. 최종 후속 변경은 UI 동작 범위로 관련 검사·새 production E2E 빌드로 검증했고 전체197개를 최신코드로 다시 실행했다고 표현하지 않는다.


### 후속 범위 최종 직접 확인

독립 UX/UI 리뷰어 모두 최종 매핑과 관리 추가를 실제 서버에서 확인하고 필수 문제 없이 종료했다. 직접 조작은 공개 seed가 있는 author 관리 카드, 요청한 learner URL은 제공된 E2E fixture 캡처로 확인했다. 평가 클릭 중 URL 유지·선택1·새로고침 복원·별도 관리 버튼 진입을 확인했다. UX 좌표는320px에서 풀이 평가 x37, 태그/관리 평가 x≈150. `/tmp/ux-final-manage.png`, `/tmp/ui-final-{1280,320}-{manage,tag,solve}.png`. 관리 진입을 링크/정확한 단어로 가정했던 첫 리뷰 스크립트는 실제 버튼의 접근 가능한 이름으로 수정해 확인했으며 앱 결함이 아니다. 최종 필수 미해결 문제 없음. 실제 음성 출력 및 모든 오류/테마 조합은 미확인이다.
